# AI 기본 개념 학습 문서

## 문서 목적

이 문서는 RAG, LangChain, VectorDB, MCP, AI Agent, Web Service Flow의 기본 개념을 말로 설명할 수 있는 수준으로 정리한 학습용 문서입니다.

목표는 각 기술을 깊게 구현하는 것이 아니라, 다음 질문에 답할 수 있는 수준까지 이해하는 것입니다.

- 이 개념이 무엇인가?
- 왜 필요한가?
- 어떤 흐름으로 동작하는가?
- 실제 서비스에서는 어디에 쓰이는가?
- 한계나 주의할 점은 무엇인가?

---

# 1. RAG

## 1.1 개념 정의

RAG는 Retrieval-Augmented Generation의 약자입니다.

한국어로 풀면 **검색 증강 생성** 정도로 이해할 수 있습니다.

RAG는 LLM이 자기 학습 지식만으로 답하는 것이 아니라, 외부 문서나 데이터베이스에서 관련 정보를 먼저 검색한 뒤, 그 내용을 참고해서 답변을 생성하는 방식입니다.

즉, RAG는 다음 두 가지를 결합한 구조입니다.

```text
검색 Retrieval
+
생성 Generation
```

LLM이 모든 정보를 기억하고 있다고 가정하지 않고, 필요한 정보를 외부에서 찾아서 답변에 활용하는 방식입니다.

---

## 1.2 왜 필요한가?

LLM은 강력하지만 몇 가지 한계가 있습니다.

첫째, 모델이 학습한 시점 이후의 최신 정보를 모를 수 있습니다.

둘째, 회사 내부 문서, 개인 문서, 계약서, 업무 매뉴얼처럼 공개되지 않은 정보는 기본 모델이 알 수 없습니다.

셋째, 모델이 모르는 내용을 그럴듯하게 만들어내는 hallucination 문제가 발생할 수 있습니다.

RAG는 이런 문제를 줄이기 위해 사용됩니다.

예를 들어 회사 규정 문서를 LLM에게 전부 학습시키는 대신, 문서를 저장해두고 사용자가 질문할 때 관련 문단을 먼저 찾습니다. 그다음 LLM에게 다음과 같이 요청합니다.

```text
아래 문서를 근거로 사용자의 질문에 답변하세요.
```

이렇게 하면 LLM은 외부 문서를 참고하여 답변을 생성할 수 있습니다.

---

## 1.3 동작 흐름

RAG의 일반적인 흐름은 다음과 같습니다.

```text
문서 업로드
→ 텍스트 추출
→ 문서 분할
→ 임베딩 생성
→ VectorDB 저장
→ 사용자 질문 입력
→ 질문 임베딩 생성
→ 관련 문서 검색
→ 검색 결과와 질문을 LLM에 전달
→ 답변 생성
→ 사용자에게 응답
```

조금 더 쉽게 말하면 다음과 같습니다.

1. 문서를 준비합니다.
2. 문서를 작은 조각으로 나눕니다.
3. 각 조각을 숫자 벡터로 변환합니다.
4. 벡터를 VectorDB에 저장합니다.
5. 사용자가 질문합니다.
6. 질문도 벡터로 변환합니다.
7. 질문과 의미가 비슷한 문서 조각을 찾습니다.
8. 찾은 문서 조각을 LLM에게 같이 전달합니다.
9. LLM이 문서를 참고해서 답변합니다.

---

## 1.4 실제 예시

예를 들어 사용자가 계약서 PDF를 업로드하고 다음과 같이 질문한다고 가정합니다.

```text
이 계약서에서 위약금 조항은 어떻게 되어 있나요?
```

RAG 기반 서비스는 다음 순서로 동작합니다.

```text
계약서 PDF 업로드
→ PDF 텍스트 추출
→ 조항 단위로 분할
→ 각 조항을 임베딩으로 변환
→ VectorDB 저장
→ 사용자 질문 입력
→ 질문 임베딩
→ 위약금과 관련된 조항 검색
→ 검색된 조항과 질문을 LLM에 전달
→ 위약금 조항 요약 답변 생성
```

이 구조를 사용하면 LLM이 계약서 전체를 무작정 읽는 것이 아니라, 질문과 관련된 부분을 먼저 찾고 그 부분을 중심으로 답변할 수 있습니다.

---

## 1.5 장점과 한계

## 장점

- 모델이 원래 모르는 외부 문서를 활용할 수 있습니다.
- 최신 정보나 사내 데이터를 반영할 수 있습니다.
- 답변의 근거 문서를 함께 제시할 수 있습니다.
- 모델을 매번 재학습하지 않아도 됩니다.

## 한계

- 검색 결과가 부정확하면 답변도 부정확해질 수 있습니다.
- 문서 분할 방식이 좋지 않으면 필요한 정보가 잘리지 않을 수 있습니다.
- VectorDB 검색 결과가 항상 정답을 보장하지는 않습니다.
- LLM이 검색된 문서를 잘못 해석할 가능성도 있습니다.

# 2. LangChain

## 2.1 개념 정의

LangChain은 LLM 애플리케이션을 만들 때 필요한 여러 기능을 연결해주는 프레임워크입니다.

LangChain은 AI 모델 그 자체가 아닙니다.

LLM, 프롬프트, 문서 로더, 텍스트 분할기, VectorDB, 검색기, Agent, 외부 도구 등을 하나의 흐름으로 연결하기 쉽게 도와주는 도구 모음에 가깝습니다.

---

## 2.2 왜 필요한가?

LLM을 실제 서비스에서 사용하려면 단순히 API 한 번 호출하는 것보다 더 많은 처리가 필요합니다.

예를 들어 RAG 서비스를 만들려면 다음 작업들이 필요합니다.

```text
문서 로딩
→ 텍스트 분할
→ 임베딩 생성
→ VectorDB 저장
→ 검색기 구성
→ 프롬프트 작성
→ LLM 호출
→ 답변 후처리
```

이 과정을 직접 모두 구현할 수도 있지만, 반복되는 부분이 많습니다.

LangChain은 이런 작업을 부품처럼 조합할 수 있게 도와줍니다.

---

## 2.3 동작 방식

LangChain은 여러 구성 요소를 연결해서 하나의 체인을 만듭니다.

예를 들어 RAG 구조에서는 다음과 같은 흐름을 만들 수 있습니다.

```text
사용자 질문
→ Retriever가 관련 문서 검색
→ Prompt Template에 질문과 문서 삽입
→ LLM 호출
→ 답변 반환
```

여기서 LangChain은 각각의 단계를 쉽게 연결할 수 있도록 도와줍니다.

---

## 2.4 실제 예시

문서 기반 질의응답 서비스를 만든다고 가정합니다.

LangChain을 사용하면 다음과 같은 기능을 조합할 수 있습니다.

- PDF 문서를 읽는 Document Loader
- 긴 문서를 나누는 Text Splitter
- 문서를 벡터로 바꾸는 Embedding Model
- 벡터를 저장하는 Vector Store
- 관련 문서를 검색하는 Retriever
- 질문과 문서를 합치는 Prompt Template
- 답변을 생성하는 LLM

이런 구성 요소를 연결하면 RAG 서비스를 더 빠르게 만들 수 있습니다.

---

## 2.5 장점과 한계

## 장점

- LLM 애플리케이션의 반복적인 구현을 줄일 수 있습니다.
- RAG, Agent, Tool Calling 같은 구조를 빠르게 실험할 수 있습니다.
- 다양한 LLM, VectorDB, 외부 도구와 연결할 수 있습니다.
- 프로토타입을 빠르게 만들기 좋습니다.

## 한계

- 내부 구조를 모르면 디버깅이 어려울 수 있습니다.
- 작은 프로젝트에서는 오히려 복잡해질 수 있습니다.
- 추상화가 많아서 실제 동작 흐름을 놓칠 수 있습니다.
- 버전 변화에 따라 코드가 자주 바뀔 수 있습니다.

# 3. VectorDB

## 3.1 개념 정의

VectorDB는 데이터를 벡터 형태로 저장하고, 벡터 간 유사도를 기준으로 검색할 수 있는 데이터베이스입니다.

텍스트, 이미지, 문서, 코드 등을 임베딩 모델을 통해 숫자 배열로 바꾸면 벡터가 됩니다.

예를 들어 문장 하나를 다음과 같은 숫자 배열로 표현할 수 있습니다.

```text
[0.12, -0.03, 0.87, 0.44, ...]
```

VectorDB는 이런 벡터들을 저장하고, 사용자의 질문 벡터와 의미적으로 가까운 벡터를 찾아줍니다.

---

## 3.2 왜 필요한가?

일반적인 DB 검색은 정확한 키워드나 조건에 의존합니다.

예를 들어 SQL에서는 다음과 같이 검색할 수 있습니다.

```sql
SELECT * FROM documents
WHERE content LIKE '%퇴사%';
```

하지만 사용자가 “회사를 그만둘 때 남은 휴가는 어떻게 되나요?”라고 질문했을 때, 문서에는 “미사용 연차 정산”이라는 표현만 있을 수 있습니다.

키워드는 다르지만 의미는 비슷합니다.

VectorDB는 이런 의미 기반 검색에 사용됩니다.

---

## 3.3 동작 흐름

VectorDB를 사용하는 일반적인 흐름은 다음과 같습니다.

```text
문서 텍스트 준비
→ 임베딩 모델로 벡터 변환
→ VectorDB에 벡터와 원문 저장
→ 사용자 질문 입력
→ 질문을 벡터로 변환
→ VectorDB에서 가까운 벡터 검색
→ 관련 문서 반환
```

핵심은 문서와 질문을 같은 벡터 공간에 넣고, 서로 가까운 것을 찾는 것입니다.

---

## 3.4 실제 예시

문서에 다음 내용이 저장되어 있다고 가정합니다.

```text
직원이 퇴사하는 경우 사용하지 않은 연차휴가는 급여와 함께 정산한다.
```

사용자가 이렇게 질문합니다.

```text
퇴사할 때 남은 휴가는 어떻게 처리되나요?
```

두 문장은 단어가 완전히 같지는 않습니다.

하지만 의미가 비슷하기 때문에 임베딩 벡터 공간에서는 서로 가까운 위치에 놓일 가능성이 높습니다.

VectorDB는 이 유사도를 기준으로 관련 문서를 찾아줍니다.

---

## 3.5 장점과 한계

## 장점

- 키워드가 정확히 일치하지 않아도 의미 기반 검색이 가능합니다.
- RAG에서 관련 문서를 찾는 핵심 저장소로 사용할 수 있습니다.
- 문서, 이미지, 코드 등 다양한 데이터를 검색할 수 있습니다.
- 추천 시스템이나 유사 문서 검색에도 활용할 수 있습니다.

## 한계

- 임베딩 모델의 품질에 따라 검색 품질이 달라집니다.
- 의미가 비슷하지만 실제로는 다른 문서가 검색될 수 있습니다.
- 최신 데이터 반영을 위해 벡터를 다시 생성해야 할 수 있습니다.
- 일반 DB처럼 정교한 조건 검색만으로 해결되는 문제에는 과할 수 있습니다.

# 4. MCP

## 4.1 개념 정의

MCP는 Model Context Protocol의 약자입니다.

MCP는 AI 모델이나 AI Agent가 외부 도구, 파일, DB, API 등에 연결되는 방식을 표준화하려는 프로토콜입니다.

쉽게 말하면, AI가 외부 시스템을 사용할 수 있도록 연결 규칙을 정해주는 방식입니다.

---

## 4.2 왜 필요한가?

AI가 실제 업무를 수행하려면 단순히 텍스트만 생성해서는 부족합니다.

예를 들어 AI가 다음과 같은 일을 하려면 외부 시스템에 접근해야 합니다.

- 로컬 파일 읽기
- GitHub 이슈 조회
- Notion 문서 작성
- Slack 메시지 검색
- DB 조회
- 브라우저 자동화
- 캘린더 일정 확인

각 도구마다 연결 방식이 다르면 AI 앱마다 별도의 연동 코드를 작성해야 합니다.

MCP는 이런 연결 방식을 표준화해서, AI 클라이언트와 외부 도구 서버가 일정한 방식으로 통신할 수 있게 합니다.

---

## 4.3 기본 구조

MCP는 보통 다음과 같은 구조로 이해할 수 있습니다.

```text
AI 애플리케이션
→ MCP Client
→ MCP Server
→ 외부 도구 / 파일 / DB / API
```

각 역할은 다음과 같습니다.

- AI 애플리케이션: 사용자가 실제로 사용하는 AI 프로그램입니다.
- MCP Client: AI 애플리케이션 안에서 MCP 서버와 통신하는 구성 요소입니다.
- MCP Server: 특정 도구나 데이터에 접근하는 기능을 제공합니다.
- 외부 도구: 파일 시스템, DB, GitHub, Slack, Notion 같은 실제 자원입니다.

---

## 4.4 실제 예시

예를 들어 AI가 사용자의 로컬 프로젝트 파일을 읽고 코드를 분석한다고 가정합니다.

MCP가 없다면 AI 앱이 직접 파일 접근 기능을 구현해야 합니다.

MCP를 사용하면 파일 시스템에 접근하는 MCP Server를 실행하고, AI 앱은 MCP Client를 통해 그 서버에 요청합니다.

흐름은 다음과 같습니다.

```text
사용자: 이 프로젝트 구조를 분석해줘
→ AI 앱이 파일 목록 조회 필요성을 판단
→ MCP Client가 파일 시스템 MCP Server에 요청
→ MCP Server가 파일 목록과 파일 내용을 반환
→ AI가 내용을 분석
→ 사용자에게 설명
```

---

## 4.5 장점과 한계

## 장점

- AI와 외부 도구의 연결 방식을 표준화할 수 있습니다.
- 여러 AI 앱에서 같은 MCP Server를 재사용할 수 있습니다.
- 파일, DB, API, 업무 도구 등을 AI와 연결하기 쉬워집니다.
- AI Agent가 실제 작업을 수행할 수 있는 기반이 됩니다.

## 한계

- 외부 시스템 접근 권한을 다루기 때문에 보안이 중요합니다.
- 잘못 설정하면 민감한 파일이나 데이터에 접근할 위험이 있습니다.
- 악성 MCP Server나 prompt injection 공격 가능성을 고려해야 합니다.
- 아직 생태계가 빠르게 변화하는 단계라 구현 방식이 바뀔 수 있습니다.

# 5. AI Agent

## 5.1 개념 정의

AI Agent는 사용자의 목표를 이해하고, 필요한 작업을 스스로 나누고, 도구를 사용하면서 여러 단계를 수행하는 AI 시스템입니다.

일반 챗봇은 질문에 대해 한 번 답변하는 구조에 가깝습니다.

반면 AI Agent는 다음과 같은 기능을 가질 수 있습니다.

- 목표 이해
- 계획 수립
- 도구 선택
- 실행
- 결과 확인
- 필요 시 반복
- 최종 답변 생성

즉, AI Agent는 단순한 답변 생성기가 아니라, 작업 수행형 AI에 가깝습니다.

---

## 5.2 왜 필요한가?

실제 업무는 한 번의 답변으로 끝나지 않는 경우가 많습니다.

예를 들어 사용자가 다음과 같이 요청할 수 있습니다.

```text
이번 주 회의록을 요약하고, TODO를 뽑아서 Notion에 정리해줘.
```

이 요청을 수행하려면 여러 단계가 필요합니다.

```text
회의록 찾기
→ 회의록 읽기
→ 핵심 내용 요약
→ TODO 추출
→ 담당자 분류
→ Notion 문서 작성
→ 결과 확인
```

AI Agent는 이런 여러 단계를 수행하기 위해 사용됩니다.

---

## 5.3 동작 흐름

AI Agent의 일반적인 흐름은 다음과 같습니다.

```text
사용자 목표 입력
→ Agent가 목표 해석
→ 필요한 작업 계획
→ 사용할 도구 선택
→ 도구 실행
→ 실행 결과 확인
→ 추가 작업 판단
→ 최종 결과 반환
```

예를 들어 코딩 Agent는 다음과 같이 동작할 수 있습니다.

```text
사용자: 로그인 오류를 고쳐줘
→ 프로젝트 파일 탐색
→ 관련 코드 검색
→ 오류 원인 추론
→ 코드 수정
→ 테스트 실행
→ 실패 시 재수정
→ 변경 내용 요약
```

---

## 5.4 실제 사용 예시

AI Agent는 다음과 같은 영역에서 사용될 수 있습니다.

- 코딩 보조 Agent
- 문서 검색 Agent
- 고객지원 자동화 Agent
- 데이터 분석 Agent
- 이메일 분류 Agent
- 일정 관리 Agent
- 브라우저 자동화 Agent
- 업무 보고서 작성 Agent

예를 들어 코딩 Agent는 단순히 코드 예시를 보여주는 것이 아니라, 실제 프로젝트 파일을 읽고 수정하고 테스트할 수 있습니다.

## 5.5 장점과 한계

## 장점

- 반복적인 업무를 자동화할 수 있습니다.
- 여러 도구를 조합해 복잡한 작업을 처리할 수 있습니다.
- 사용자는 목표만 말하고 세부 단계는 Agent가 처리하게 할 수 있습니다.
- 문서, 코드, DB, API 등 다양한 자원을 활용할 수 있습니다.

## 한계

- 잘못된 계획을 세울 수 있습니다.
- 잘못된 도구를 호출할 수 있습니다.
- 권한이 큰 작업에서는 위험할 수 있습니다.
- 실행 결과를 검증하지 않으면 오류가 누적될 수 있습니다.
- 비용과 속도 문제가 발생할 수 있습니다.

# 6. Web Service Flow

## 6.1 개념 정의

Web Service Flow는 사용자가 웹 페이지에서 어떤 행동을 했을 때, 그 요청이 프론트엔드, 백엔드, DB를 거쳐 다시 화면에 반영되는 전체 흐름입니다.

웹 서비스를 이해하려면 다음 요소들의 역할을 구분해야 합니다.

- 사용자
- 브라우저
- 프론트엔드
- 백엔드
- API
- 데이터베이스
- 인증 시스템
- 서버 응답
- 화면 렌더링

---

## 6.2 기본 흐름

가장 기본적인 웹 서비스 흐름은 다음과 같습니다.

```text
사용자 행동
→ 브라우저 / 프론트엔드
→ API 요청
→ 백엔드 라우터 / 컨트롤러
→ 서비스 로직
→ DB 조회 / 저장
→ 백엔드 응답
→ 프론트엔드 상태 변경
→ 화면 반영
```

예를 들어 사용자가 게시글 작성 버튼을 누르면 다음 흐름이 발생합니다.

```text
사용자가 제목과 내용을 입력
→ 작성 버튼 클릭
→ 프론트엔드가 POST 요청 전송
→ 백엔드가 요청 수신
→ 입력값 검증
→ DB에 게시글 저장
→ 저장 성공 응답 반환
→ 프론트엔드가 게시글 목록 갱신
→ 화면에 새 게시글 표시
```

---

## 6.3 로그인 예시

로그인 기능을 기준으로 보면 흐름은 다음과 같습니다.

```text
사용자가 이메일과 비밀번호 입력
→ 로그인 버튼 클릭
→ 프론트엔드가 로그인 API 요청
→ 백엔드가 사용자 정보 조회
→ 비밀번호 검증
→ 인증 토큰 또는 세션 생성
→ 프론트엔드에 응답 반환
→ 프론트엔드가 로그인 상태 저장
→ 메인 페이지로 이동
```

이 과정에서 프론트엔드와 백엔드의 역할은 다릅니다.

프론트엔드는 사용자 입력을 받고 화면을 보여줍니다.

백엔드는 실제 검증, DB 조회, 인증 처리, 비즈니스 로직을 담당합니다.

DB는 사용자 정보나 게시글 같은 데이터를 저장합니다.

---

## 6.4 프론트엔드와 백엔드 역할

## 프론트엔드

프론트엔드는 사용자가 직접 보는 화면입니다.

주요 역할은 다음과 같습니다.

- 화면 구성
- 버튼, 입력창, 폼 처리
- 사용자 이벤트 처리
- 백엔드 API 호출
- 응답 데이터를 화면에 표시
- 로그인 상태에 따른 화면 변경

## 백엔드

백엔드는 서버에서 실행되는 로직입니다.

주요 역할은 다음과 같습니다.

- API 요청 수신
- 입력값 검증
- 비즈니스 로직 처리
- DB 조회 및 저장
- 인증과 권한 확인
- 외부 API 호출
- 응답 생성

## 데이터베이스

DB는 데이터를 저장하고 조회하는 역할을 합니다.

주요 데이터 예시는 다음과 같습니다.

- 사용자 정보
- 게시글
- 댓글
- 결제 내역
- 업로드 파일 정보
- 서비스 로그

# 7. 실제 서비스 유저 시나리오

## 7.1 예시 서비스: 문서 기반 질의응답 서비스

예시 서비스로 문서 기반 질의응답 서비스를 생각해볼 수 있습니다.

이 서비스는 사용자가 PDF 문서를 업로드하고, 문서 내용에 대해 질문하면 AI가 답변해주는 서비스입니다.

---

## 7.2 사용자 시나리오

사용자 시나리오는 다음과 같습니다.

```text
1. 사용자가 웹 서비스에 접속한다.
2. 사용자가 PDF 문서를 업로드한다.
3. 서비스가 PDF에서 텍스트를 추출한다.
4. 서비스가 문서를 작은 조각으로 나눈다.
5. 각 문서 조각을 임베딩으로 변환한다.
6. 임베딩 결과를 VectorDB에 저장한다.
7. 사용자가 문서에 대해 질문한다.
8. 서비스가 질문을 임베딩으로 변환한다.
9. VectorDB에서 질문과 관련된 문서 조각을 검색한다.
10. 검색된 문서 조각과 질문을 LLM에 전달한다.
11. LLM이 문서를 근거로 답변을 생성한다.
12. 프론트엔드가 답변을 화면에 보여준다.
```

---

## 7.3 기술 연결 구조

이 서비스 안에서 각 개념은 다음과 같이 연결됩니다.

```text
Web Service Flow
사용자가 웹에서 문서를 업로드하고 질문하는 전체 흐름

RAG
질문과 관련된 문서 조각을 검색한 뒤 LLM 답변에 활용하는 구조

VectorDB
문서 조각과 질문을 벡터로 저장하고 의미 기반으로 검색하는 저장소

LangChain
문서 분할, 검색, 프롬프트 구성, LLM 호출 흐름을 연결하는 도구

AI Agent
필요하면 문서 분석, 요약, 추가 검색, 보고서 생성 같은 여러 단계를 수행하는 자동화 시스템

MCP
AI Agent가 외부 파일, DB, Notion, GitHub, Slack 같은 도구와 연결될 수 있게 하는 표준화된 연결 방식
```

---

## 7.4 전체 시스템 흐름

문서 기반 질의응답 서비스를 전체 흐름으로 보면 다음과 같습니다.

```text
사용자
→ 웹 페이지 접속
→ PDF 업로드
→ 프론트엔드가 백엔드로 파일 전송
→ 백엔드가 PDF 텍스트 추출
→ 텍스트 분할
→ 임베딩 생성
→ VectorDB 저장
→ 사용자 질문 입력
→ 프론트엔드가 질문을 백엔드로 전송
→ 백엔드가 질문 임베딩 생성
→ VectorDB에서 관련 문서 검색
→ 검색 결과와 질문을 LLM에 전달
→ LLM 답변 생성
→ 백엔드가 답변 반환
→ 프론트엔드가 화면에 답변 표시
```

# 8. 전체 요약

## 8.1 한 문장 요약

RAG는 외부 문서를 검색해서 LLM 답변에 활용하는 구조이고, VectorDB는 그 문서를 의미 기반으로 찾기 위한 저장소이며, LangChain은 이런 흐름을 연결하는 프레임워크입니다. MCP는 AI가 외부 도구와 연결되는 방식을 표준화하는 프로토콜이고, AI Agent는 도구를 사용하면서 여러 단계를 수행하는 AI 시스템입니다. Web Service Flow는 사용자의 요청이 프론트엔드, 백엔드, DB를 거쳐 다시 화면에 반영되는 전체 흐름입니다.

---

## 8.2 개념 간 관계

```text
사용자
→ Web Service
→ Backend
→ RAG
→ VectorDB 검색
→ LLM 답변 생성
→ Frontend 응답 표시
```

추가로 자동화가 필요하면 다음 개념이 연결됩니다.

```text
AI Agent
→ 필요한 작업 계획
→ MCP를 통해 외부 도구 연결
→ 파일 / DB / API / 업무 도구 사용
→ 결과 생성
```

---

## 8.3 학습 우선순위

처음부터 모든 기술을 깊게 구현할 필요는 없습니다.

우선순위는 다음과 같이 잡는 것이 적절합니다.

```text
1. Web Service Flow 이해
2. LLM이 API로 호출되는 방식 이해
3. RAG의 전체 흐름 이해
4. VectorDB의 의미 기반 검색 이해
5. LangChain이 어떤 역할을 하는지 이해
6. AI Agent가 일반 챗봇과 어떻게 다른지 이해
7. MCP가 외부 도구 연결에서 어떤 역할을 하는지 이해
```

---

## 8.4 말로 설명할 때의 핵심 문장

스터디나 발표에서 전체를 설명할 때는 다음과 같이 말할 수 있습니다.

```text
웹 서비스에서는 사용자가 프론트엔드에서 요청을 보내고, 백엔드가 DB나 외부 API를 조회한 뒤 응답을 반환합니다.

AI 기능이 들어가면 백엔드가 LLM API를 호출할 수 있고, 문서 기반 답변이 필요하면 RAG 구조를 사용합니다.

RAG에서는 문서를 임베딩으로 바꿔 VectorDB에 저장하고, 사용자의 질문과 의미적으로 가까운 문서를 검색한 뒤 LLM에게 함께 전달합니다.

LangChain은 이런 문서 처리, 검색, 프롬프트 구성, LLM 호출 과정을 연결하는 데 도움을 주는 프레임워크입니다.

AI Agent는 단순 답변을 넘어서 목표를 수행하기 위해 도구를 선택하고 여러 단계를 실행하는 AI 시스템입니다.

MCP는 이런 AI Agent나 AI 앱이 외부 파일, DB, API, 업무 도구와 연결되는 방식을 표준화하려는 프로토콜입니다.
```
