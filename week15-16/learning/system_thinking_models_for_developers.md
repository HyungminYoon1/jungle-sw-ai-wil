# 개발자를 위한 핵심 시스템 사고 모델 학습 문서

## 목적

이 문서는 개발자가 웹 서비스와 백엔드 시스템을 빠르게 이해하기 위해 반드시 익혀야 하는 핵심 사고 모델을 정리한 학습용 문서입니다.

여기서 말하는 “모델”은 머신러닝 모델이 아니라, 복잡한 시스템을 이해하기 위한 **개념적 사고 틀**입니다.

예를 들어 장애가 발생했을 때 단순히 “서버가 이상하다”라고 생각하는 것이 아니라,

```text
요청은 어디까지 도달했는가?
인증은 통과했는가?
DB 트랜잭션은 커밋되었는가?
캐시는 최신 상태인가?
비동기 작업은 실패했는가?
비용이 폭증할 구조인가?
보안 취약점은 없는가?
```

처럼 문제를 나누어 보는 방식입니다.

```text
9. 보안 위협 모델
```

# 1. HTTP 요청-응답 모델

## 1.1 개념 정의

HTTP 요청-응답 모델은 웹 서비스에서 클라이언트와 서버가 통신하는 기본 구조입니다.

```text
클라이언트 → HTTP 요청 → 서버 → 처리 → HTTP 응답 → 클라이언트
```

웹 브라우저, 모바일 앱, 프론트엔드 React/Next.js, 백엔드 API, 외부 API 호출은 대부분 이 모델 위에서 동작합니다.

---

## 1.2 작동 원리

기본 흐름은 다음과 같습니다.

```text
1. 사용자가 버튼을 클릭한다.
2. 브라우저 또는 프론트엔드 코드가 HTTP 요청을 보낸다.
3. 서버 라우터가 요청 URL과 메서드를 확인한다.
4. 서버가 인증, 입력값 검증, 비즈니스 로직을 수행한다.
5. DB 또는 외부 API를 호출한다.
6. 서버가 상태 코드와 응답 데이터를 반환한다.
7. 클라이언트가 응답을 화면에 반영한다.
```

예시:

```http
GET /api/contracts/123 HTTP/1.1
Authorization: Bearer <token>
Accept: application/json
```

응답:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": "123",
  "title": "Lease Agreement",
  "status": "analyzed"
}
```

---

## 1.3 핵심 구성요소

| 요소 | 설명 |
|---|---|
| URL | 요청 대상 리소스 |
| Method | GET, POST, PUT, PATCH, DELETE |
| Header | 인증 정보, Content-Type 등 부가 정보 |
| Body | 서버에 전달할 데이터 |
| Status Code | 요청 처리 결과 |
| Response Body | 서버가 반환하는 데이터 |

---

## 1.4 반드시 익혀야 할 상태 코드

| 코드 | 의미 | 실무 해석 |
|---:|---|---|
| 200 | OK | 요청 성공 |
| 201 | Created | 생성 성공 |
| 204 | No Content | 성공했지만 반환 데이터 없음 |
| 400 | Bad Request | 클라이언트 입력 오류 |
| 401 | Unauthorized | 인증 안 됨 |
| 403 | Forbidden | 권한 없음 |
| 404 | Not Found | 리소스 없음 |
| 409 | Conflict | 중복 또는 상태 충돌 |
| 422 | Unprocessable Entity | 유효성 검증 실패 |
| 500 | Internal Server Error | 서버 내부 오류 |
| 502 | Bad Gateway | 게이트웨이/프록시 오류 |
| 503 | Service Unavailable | 서버 또는 의존 서비스 사용 불가 |

---

## 1.5 실무에서 던져야 할 질문

```text
이 요청은 어디에서 시작되었는가?
요청 URL과 HTTP Method가 맞는가?
인증 토큰이 포함되었는가?
서버 라우터에 도달했는가?
입력값 검증에서 실패했는가?
DB 호출까지 갔는가?
응답 상태 코드는 무엇인가?
프론트엔드가 응답을 올바르게 처리했는가?
```

---

## 1.6 실제 사례

PDF 업로드 기능을 예로 들면 다음과 같습니다.

```text
사용자 → PDF 선택 → POST /api/upload → 서버 검증 → 파일 저장 → 텍스트 추출 → DB 저장 → 응답 반환
```

이때 오류가 발생하면 HTTP 요청-응답 모델로 위치를 분해합니다.

```text

요청이 전송되지 않았는가?
파일 크기 제한에 걸렸는가?
서버에서 파싱 실패했는가?
DB 저장 실패인가?
응답은 왔지만 프론트에서 표시하지 못했는가?
```

## 1.7 장점과 한계

장점:

```text

API 오류를 체계적으로 추적할 수 있다.
프론트엔드와 백엔드의 책임을 분리할 수 있다.
```

한계:

```text

```

# 2. DB 트랜잭션 모델

## 2.1 개념 정의

DB 트랜잭션은 여러 DB 작업을 하나의 논리적 작업 단위로 묶는 모델입니다.

핵심은 다음입니다.

```text
모두 성공하면 커밋
하나라도 실패하면 롤백
```

예를 들어 결제 시스템에서 다음 작업은 하나의 트랜잭션이어야 합니다.

```text
1. 주문 생성
2. 결제 기록 생성
3. 재고 차감
4. 포인트 차감
```

중간에 하나만 실패했는데 나머지가 반영되면 데이터가 깨집니다.

---

## 2.2 ACID

트랜잭션의 핵심 속성은 ACID입니다.

| 속성 | 의미 |
|---|---|
| Atomicity | 원자성. 전부 성공하거나 전부 실패 |
| Consistency | 일관성. DB 규칙을 깨지 않음 |
| Isolation | 격리성. 동시에 실행되는 트랜잭션 간 간섭 제어 |
| Durability | 지속성. 커밋된 데이터는 보존됨 |

---

## 2.3 작동 흐름

```text
BEGIN
  INSERT INTO orders ...
  UPDATE inventory ...
  INSERT INTO payment_logs ...
COMMIT
```

실패 시:

```text
BEGIN
  INSERT INTO orders ...
  UPDATE inventory ...
  -- 오류 발생
ROLLBACK
```

---

## 2.4 실무에서 중요한 문제

트랜잭션은 단순히 “묶는다”가 아니라 동시성 문제와 연결됩니다.

예를 들어 동시에 두 사용자가 마지막 재고 1개를 주문하면 어떻게 될까요?

```text
사용자 A: 재고 1 확인
사용자 B: 재고 1 확인
사용자 A: 주문 성공
사용자 B: 주문 성공
결과: 재고 -1 또는 중복 판매
```

이 문제를 막으려면 락, 격리 수준, 조건부 업데이트 등을 고려해야 합니다.

---

## 2.5 격리 수준

| 격리 수준 | 설명 |
|---|---|
| Read Uncommitted | 커밋되지 않은 데이터도 읽을 수 있음. 단, PostgreSQL에서는 실제로 Read Committed처럼 동작 |
| Read Committed | 커밋된 데이터만 읽음 |
| Repeatable Read | 같은 트랜잭션 안에서 같은 조회 결과 보장 |
| Serializable | 가장 강한 격리. 결과가 직렬 실행과 같도록 보장 |

격리 수준이 강할수록 데이터 안정성은 높아지지만 성능은 떨어질 수 있습니다.

Serializable은 모든 트랜잭션을 실제로 하나씩 실행한다는 뜻이 아닙니다. 동시에 실행하더라도 결과가 순서대로 실행한 것과 같도록 보장하는 방식입니다. 충돌이 발생하면 DB가 트랜잭션을 실패시킬 수 있고, 이 경우 애플리케이션에서 재시도 처리가 필요할 수 있습니다.

---

## 2.6 실무 질문

```text
이 작업은 하나의 트랜잭션으로 묶여야 하는가?
중간 실패 시 어떤 데이터가 남으면 안 되는가?
동시에 같은 데이터를 수정할 수 있는가?
락이 필요한가?
트랜잭션 범위가 너무 길지 않은가?
외부 API 호출을 트랜잭션 안에 넣어도 되는가?
```

주의할 점:

```text
외부 API 호출을 DB 트랜잭션 안에 오래 넣으면 락 시간이 길어지고 장애 전파 위험이 커질 수 있다.
```

# 3. 인덱스와 쿼리 플랜 모델

## 3.1 개념 정의

인덱스는 DB가 데이터를 빠르게 찾기 위한 자료구조입니다.

인덱스가 없으면 DB는 테이블을 처음부터 끝까지 훑을 수 있습니다.

```text
인덱스 없음: 전체 테이블 스캔
인덱스 있음: 필요한 위치로 빠르게 이동
```

---

## 3.2 비유

책에서 특정 단어를 찾는다고 생각하면 됩니다.

```text
색인이 없으면 모든 페이지를 읽어야 한다.
색인이 있으면 해당 단어가 있는 페이지로 바로 이동할 수 있다.
```

DB 인덱스도 비슷합니다.

---

## 3.3 쿼리 플랜

쿼리 플랜은 DB가 SQL을 실행하기 위해 선택한 실행 전략입니다.

예:

```sql
EXPLAIN ANALYZE
SELECT *
FROM uploaded_contracts
WHERE user_id = '...'
ORDER BY created_at DESC
LIMIT 20;
```

DB는 다음을 판단합니다.

```text
인덱스를 쓸 것인가?
전체 테이블을 읽을 것인가?
정렬은 어떻게 할 것인가?
조인은 어떤 순서로 할 것인가?
예상 비용은 얼마인가?
실제 실행 시간은 얼마인가?
```

---

## 3.4 인덱스가 필요한 경우

| 상황 | 인덱스 필요 가능성 |
|---|---|
| WHERE 조건에 자주 사용 | 높음 |
| JOIN 키로 자주 사용 | 높음 |
| ORDER BY에 자주 사용 | 높음 |
| UNIQUE 제약 필요 | 높음 |
| 작은 테이블 | 낮음 |
| 거의 조회하지 않는 컬럼 | 낮음 |
| 값 종류가 적은 컬럼 | 상황에 따라 다름 |

---

## 3.5 복합 인덱스

예를 들어 다음 쿼리가 많다면:

```sql
SELECT *
FROM uploaded_contracts
WHERE user_id = '...'
ORDER BY created_at DESC;
```

다음 인덱스가 유용할 수 있습니다.

```sql
CREATE INDEX idx_uploaded_contracts_user_created
ON uploaded_contracts (user_id, created_at DESC);
```

복합 인덱스에서는 컬럼 순서가 중요합니다.

```text
(user_id, created_at) 인덱스는 user_id 조건에 특히 유리하다.
created_at만 단독으로 검색할 때는 효율이 낮을 수 있다.
```

---

## 3.6 인덱스의 비용

인덱스는 공짜가 아닙니다.

| 장점 | 비용 |
|---|---|
| 조회 속도 증가 | 저장 공간 증가 |
| 정렬 성능 개선 | INSERT/UPDATE/DELETE 느려질 수 있음 |
| UNIQUE 보장 | 인덱스 관리 비용 증가 |

---

## 3.7 실무 질문

```text
이 쿼리는 얼마나 자주 실행되는가?
응답 시간이 느린 원인은 DB인가?
WHERE 조건 컬럼에 인덱스가 있는가?
ORDER BY 때문에 정렬 비용이 큰가?
LIMIT이 있어도 정렬이 먼저 발생하지 않는가?
EXPLAIN ANALYZE 결과는 어떤가?
인덱스를 추가하면 쓰기 성능이 얼마나 떨어지는가?
```

# 4. 인증·인가 모델

## 4.1 개념 정의

인증과 인가는 다릅니다.

| 개념 | 질문 | 예 |
|---|---|---|
| 인증 Authentication | 누구인가? | 로그인 |
| 인가 Authorization | 무엇을 할 수 있는가? | 관리자만 삭제 가능 |

예:

```text
인증: 이 사용자는 customer123인가?
인가: 이 사용자가 이 계약서를 삭제할 권한이 있는가?
```

---

## 4.2 일반적인 인증 흐름

```text
1. 사용자가 이메일/비밀번호로 로그인
2. 서버 또는 인증 서비스가 사용자를 확인
3. access token 발급
4. 클라이언트가 요청마다 token 포함
5. 서버가 token 검증
6. 사용자 ID를 기반으로 리소스 접근 판단
```

---

## 4.3 인가 모델 종류

| 모델 | 설명 |
|---|---|
| RBAC | Role-Based Access Control. 역할 기반 |
| ABAC | Attribute-Based Access Control. 속성 기반 |
| ACL | Access Control List. 리소스별 권한 목록 |
| RLS | Row-Level Security. DB 행 단위 접근 제어 |

---

## 4.4 RBAC 예시

```text
admin: 모든 데이터 관리 가능
editor: 법령 업로드/수정 요청 가능
user: 본인 계약서만 조회 가능
```

---

## 4.5 RLS 개념

RLS는 Row-Level Security의 약자로, 테이블의 각 행마다 접근 조건을 걸어 DB 레벨에서 조회, 수정, 삭제 가능 여부를 제한하는 방식입니다.

예를 들어 계약서 테이블에서 현재 사용자 ID와 `uploaded_by`가 같은 행만 조회할 수 있도록 정책을 둘 수 있습니다. 구체적인 정책 문법과 현재 사용자 식별 방식은 사용하는 DB, 인증 구조, 애플리케이션 설정에 따라 달라집니다.

핵심은 애플리케이션 코드만 믿지 않고 DB 레벨에서도 권한을 제한하는 것입니다.

---

## 4.6 실무 질문

```text
로그인한 사용자와 익명 사용자를 어떻게 구분하는가?
이 API는 인증이 필요한가?
이 사용자가 이 리소스의 소유자인가?
관리자 권한은 어디에서 검증하는가?
프론트엔드에서 버튼을 숨기는 것만으로 충분한가?
DB 레벨에서도 접근이 차단되는가?
토큰 만료와 갱신은 어떻게 처리하는가?
```

---

## 4.7 흔한 실수

```text
프론트엔드에서 버튼만 숨기고 서버 권한 검사를 하지 않음
user_id를 클라이언트에서 받아 그대로 신뢰함
관리자 API에 인증만 있고 인가가 없음
RLS 없이 Supabase 테이블을 public으로 열어둠
access token을 localStorage에 저장하고 XSS 방어를 하지 않음
```

# 5. 비동기 처리 모델

## 5.1 개념 정의

비동기 처리는 요청을 받은 즉시 모든 작업을 끝내지 않고, 오래 걸리는 작업을 뒤로 넘기는 모델입니다.

예:

```text
PDF 업로드는 즉시 응답
텍스트 추출과 GPT 분석은 백그라운드에서 처리
완료되면 상태 업데이트
```

---

## 5.2 왜 필요한가?

동기 처리만 사용하면 다음 문제가 생깁니다.

```text
사용자가 응답을 오래 기다림
서버 타임아웃 발생
외부 API 지연이 전체 요청을 막음
동시에 많은 요청이 오면 서버가 멈춤
```

---

## 5.3 기본 흐름

```text
1. 사용자가 PDF 업로드
2. 서버가 파일 저장
3. DB에 status = pending 기록
4. 작업 큐에 분석 작업 등록
5. 서버는 즉시 202 Accepted 응답
6. 워커가 큐에서 작업을 가져와 처리
7. 완료 후 status = completed 업데이트
8. 사용자가 결과 조회
```

---

## 5.4 상태 모델

비동기 작업에는 상태가 필요합니다.

```text
pending → processing → completed
                   ↘ failed
```

예시 테이블 컬럼:

```text
id
user_id
file_path
status
error_message
created_at
started_at
completed_at
```

---

## 5.5 실무 질문

```text
이 작업은 요청 중 즉시 끝나야 하는가?
사용자가 기다릴 수 있는 최대 시간은 얼마인가?
실패하면 재시도할 것인가?
같은 작업이 중복 실행되면 어떻게 할 것인가?
작업 상태를 어디에 저장할 것인가?
작업 완료를 사용자에게 어떻게 알릴 것인가?
```

---

## 5.6 주의할 문제

비동기 처리에서 중요한 문제는 다음입니다.

| 문제 | 설명 |
|---|---|
| 중복 실행 | 같은 작업이 두 번 처리됨 |
| 순서 보장 | 먼저 들어온 작업이 먼저 끝나지 않을 수 있음 |
| 재시도 폭주 | 실패 작업이 계속 재시도되어 시스템 부하 |
| 상태 불일치 | DB 상태와 실제 작업 상태가 다름 |
| 관측성 부족 | 어디서 멈췄는지 모름 |

# 6. 캐시 일관성 모델

## 6.1 개념 정의

캐시는 자주 쓰는 데이터를 빠르게 제공하기 위해 임시로 저장하는 구조입니다.

```text
원본 데이터: DB
복사본: Cache
```

문제는 원본이 바뀌었을 때 캐시가 어느 정도까지 오래된 데이터를 보여줘도 되는지, 그리고 언제 캐시를 삭제하거나 갱신할지 정해야 한다는 점입니다.

이것이 캐시 일관성 문제입니다. 캐시 일관성은 캐시가 항상 최신이어야 한다는 뜻이 아니라, 서비스가 허용할 수 있는 오래된 데이터의 범위와 무효화 전략을 정하는 문제입니다.

---

## 6.2 캐시가 필요한 이유

```text
DB 부하 감소
응답 속도 개선
외부 API 호출 비용 감소
반복 계산 제거
```

예:

```text
법령 목록
사용자 프로필
자주 조회되는 계약서 분석 결과
외부 API 응답
```

---

## 6.3 기본 패턴

### Cache-Aside

가장 흔한 패턴입니다.

```text
1. 캐시에서 조회
2. 없으면 DB 조회
3. DB 결과를 캐시에 저장
4. 응답 반환
```

의사코드:

```python
data = cache.get(key)

if data is None:
    data = db.query(...)
    cache.set(key, data, ttl=300)

return data
```

---

## 6.4 캐시 무효화

원본 데이터가 변경되면 캐시를 삭제하거나 갱신해야 합니다.

```text
계약서 제목 수정
→ DB 업데이트
→ 해당 계약서 캐시 삭제
```

---

## 6.5 TTL

TTL은 캐시의 유효 시간입니다.

```text
TTL = 300초
→ 5분 후 캐시 자동 만료
```

TTL이 짧으면 최신성은 높지만 캐시 효과가 줄어듭니다.  
TTL이 길면 성능은 좋아지지만 오래된 데이터를 보여줄 위험이 커집니다.

---

## 6.6 실무 질문

```text
이 데이터는 캐시해도 되는가?
오래된 데이터를 보여줘도 되는가?
몇 초 또는 몇 분까지 허용 가능한가?
데이터가 변경될 때 캐시를 어떻게 무효화할 것인가?
사용자별 캐시와 전체 캐시를 구분했는가?
권한이 다른 사용자에게 같은 캐시를 보여주면 안 되지 않는가?
```

---

## 6.7 흔한 실수

```text
사용자별 데이터인데 공통 캐시 키를 사용함
DB 업데이트 후 캐시 삭제를 안 함
TTL이 너무 길어 오래된 데이터가 계속 보임
캐시 장애 시 전체 서비스가 멈춤
민감한 데이터를 캐시에 저장함
```

# 7. 장애 전파 모델

## 7.1 개념 정의

장애 전파 모델은 시스템의 한 부분에서 발생한 장애가 다른 부분으로 퍼지는 과정을 이해하는 모델입니다.

예:

```text
외부 GPT API 지연
→ 백엔드 요청 대기 증가
→ 서버 스레드/커넥션 고갈
→ 전체 API 응답 지연
→ 사용자가 재시도
→ 트래픽 증가
→ 장애 확대
```

---

## 7.2 장애는 보통 연결을 타고 퍼진다

현대 웹 서비스는 여러 의존성을 가집니다.

```text
프론트엔드
백엔드
DB
스토리지
인증 서비스
결제 서비스
외부 AI API
이메일 서비스
메시지 큐
캐시 서버
```

어느 하나가 느려지면 전체 시스템에 영향을 줄 수 있습니다.

---

## 7.3 주요 방어 기법

| 기법 | 설명 |
|---|---|
| Timeout | 일정 시간 넘으면 포기 |
| Retry | 실패 시 재시도 |
| Backoff | 재시도 간격을 점점 늘림 |
| Circuit Breaker | 계속 실패하면 호출 차단 |
| Bulkhead | 장애 영역 격리 |
| Rate Limit | 요청량 제한 |
| Queue | 부하를 완충 |
| Fallback | 대체 응답 제공 |

---

## 7.4 Retry의 위험

재시도는 항상 좋은 것이 아닙니다.

```text
외부 API가 느림
→ 서버가 재시도
→ 요청 수가 3배 증가
→ 외부 API 더 느려짐
→ 전체 장애 확대
```

그래서 재시도에는 제한과 backoff가 필요합니다.

---

## 7.5 실무 질문

```text
이 API가 실패하면 전체 기능이 멈추는가?
외부 서비스 호출에 timeout이 있는가?
재시도 횟수는 제한되어 있는가?
장애가 발생했을 때 대체 응답이 가능한가?
큐가 쌓이면 어디까지 버틸 수 있는가?
한 사용자의 대량 요청이 전체 시스템에 영향을 주는가?
```

# 8. 비용 구조 모델

## 8.1 개념 정의

비용 구조 모델은 기능 하나가 실제로 어떤 비용을 발생시키는지 계산하는 사고 모델입니다.

개발자는 기능이 “동작하는가”만 보면 안 됩니다.

```text
이 기능은 사용자 1명당 얼마의 비용을 발생시키는가?
사용자가 100명, 1,000명, 10,000명이 되면 비용은 어떻게 증가하는가?
```

---

## 8.2 비용 구성요소

| 항목 | 예 |
|---|---|
| 서버 비용 | EC2, Vercel, Render |
| DB 비용 | Supabase, RDS |
| 스토리지 비용 | S3, Supabase Storage |
| 트래픽 비용 | 업로드/다운로드 |
| 외부 API 비용 | OpenAI API, OCR API |
| 백그라운드 작업 비용 | Worker, Queue |
| 로그/모니터링 비용 | Datadog, CloudWatch |
| 인건비 | 운영, 고객지원, 유지보수 |

---

## 8.3 AI 서비스의 비용 구조

AI 서비스에서는 특히 다음이 중요합니다.

```text
문서 길이
토큰 수
분석 횟수
재분석 여부
사용자당 업로드 수
모델 단가
캐싱 여부
```

예:

```text
계약서 1개 분석 비용 =
텍스트 추출 비용
+ 조항 분할 비용
+ 조항별 GPT 분석 비용
+ 전체 위험 분석 비용
+ 결과 저장 비용
```

---

## 8.4 실무 질문

```text
사용자 1명이 평균 몇 번 이 기능을 쓰는가?
요청 1회당 DB 쿼리는 몇 번 발생하는가?
GPT 호출은 몇 번 발생하는가?
토큰 수가 문서 길이에 비례해서 증가하는가?
무료 사용자가 비용을 과도하게 발생시킬 수 있는가?
캐시로 줄일 수 있는 비용인가?
비용이 매출보다 빠르게 증가하지 않는가?
```

---

## 8.5 단순 계산식

```text
월 비용 =
사용자 수 × 사용자당 평균 사용량 × 요청당 평균 비용
+ 고정 인프라 비용
+ 운영 비용
```

예:

```text
1,000명 × 월 3건 분석 × 건당 0.15달러 = 450달러
```

여기에 서버, DB, 스토리지, 로그, 결제 수수료, 고객지원 비용이 추가됩니다.

# 9. 보안 위협 모델

## 9.1 개념 정의

보안 위협 모델은 공격자가 시스템을 어떻게 악용할 수 있는지 미리 상상하고 방어하는 사고 모델입니다.

핵심 질문은 다음입니다.

```text
누가 공격자인가?
무엇을 얻으려 하는가?
어떤 경로로 공격할 수 있는가?
피해는 무엇인가?
어떻게 막을 것인가?
```

---

## 9.2 기본 공격 표면

웹 서비스의 공격 표면은 다음과 같습니다.

```text
로그인
회원가입
파일 업로드
API 요청
관리자 페이지
DB 접근
외부 API 연동
결제
검색 기능
프롬프트 입력
```

---

## 9.3 대표 위협

| 위협 | 설명 |
|---|---|
| SQL Injection | 입력값으로 SQL 조작 |
| XSS | 악성 스크립트 삽입 |
| CSRF | 사용자의 권한으로 의도치 않은 요청 실행 |
| IDOR | 다른 사용자의 리소스 ID로 접근 |
| 인증 우회 | 로그인 없이 보호 리소스 접근 |
| 권한 상승 | 일반 사용자가 관리자 기능 사용 |
| 파일 업로드 공격 | 악성 파일 업로드 |
| Prompt Injection | AI 시스템 지시를 우회하도록 입력 |
| Data Leakage | 민감 정보 유출 |
| Rate Limit 우회 | 대량 요청으로 비용/장애 유발 |

---

## 9.4 IDOR 예시

가장 흔한 실수 중 하나입니다.

```http
GET /api/contracts/123
```

서버가 단순히 ID 123만 보고 계약서를 반환하면 문제가 됩니다.

반드시 확인해야 합니다.

```text

```

## 9.6 AI 서비스의 특수 위협

AI 서비스를 만들 때는 일반 웹 보안 외에 다음도 고려해야 합니다.


# 10. 9개 모델을 함께 사용하는 방법


## 10.5 인덱스와 쿼리 플랜

```text
user_id + created_at 기준으로 사용자 문서 목록을 빠르게 조회
```

## 10.6 캐시 일관성

```text
7단계: 장애 전파 모델
8단계: 비용 구조 모델
9단계: 보안 위협 모델
```

이유는 다음입니다.

```text
HTTP를 알아야 API 흐름을 이해한다.
인증·인가를 알아야 사용자별 데이터 보호를 이해한다.
트랜잭션을 알아야 데이터 정합성을 지킨다.
인덱스를 알아야 성능 문제를 해결한다.
비동기를 알아야 오래 걸리는 작업을 처리한다.
캐시를 알아야 속도와 일관성의 trade-off를 이해한다.
장애 전파를 알아야 시스템이 무너지지 않게 설계한다.
비용 구조를 알아야 서비스가 지속 가능하다.
보안 위협을 알아야 실제 운영이 가능하다.
```

# 13. 기능 설계 체크리스트

새 기능을 만들 때 아래 질문을 순서대로 확인합니다.

```text
[HTTP]
- 어떤 API가 필요한가?
- 요청과 응답 형식은 무엇인가?
- 실패 시 어떤 상태 코드를 반환하는가?

[인증·인가]
- 로그인 필요 여부는?
- 이 사용자가 이 리소스에 접근할 수 있는가?
- 관리자 권한은 어디서 검증하는가?

[DB 트랜잭션]
- 여러 DB 작업을 하나로 묶어야 하는가?
- 중간 실패 시 롤백되어야 하는가?
- 동시 수정 문제가 있는가?

[인덱스]
- 자주 조회되는 조건은 무엇인가?
- 정렬 기준은 무엇인가?
- 쿼리 플랜을 확인했는가?

[비동기]
- 요청 중 바로 끝낼 수 있는가?
- 오래 걸리면 큐로 넘겨야 하는가?
- 작업 상태를 저장하는가?

[캐시]
- 캐시해도 되는 데이터인가?
- 오래된 데이터 허용 범위는?
- 변경 시 무효화 전략은?

[장애]
- 외부 서비스가 느리면 어떻게 되는가?
- timeout, retry, fallback이 있는가?
- 장애가 전체 시스템으로 퍼지지 않는가?

[비용]
- 요청 1회당 비용은 얼마인가?
- 사용량이 늘면 비용은 선형 증가하는가?
- 무료 사용자가 비용을 폭증시킬 수 있는가?

[보안]
- 입력값 검증이 있는가?
- IDOR 가능성은 없는가?
- 민감 정보가 로그에 남는가?
- 파일 업로드 공격을 막는가?
- 프롬프트 인젝션을 고려했는가?
```

# 14. 핵심 요약

이 9개 모델은 개발자가 시스템을 보는 기본 렌즈입니다.

```text
HTTP 요청-응답 모델:
요청이 어디서 시작되어 어디서 끝나는지 본다.

DB 트랜잭션 모델:
데이터 변경이 전부 성공하거나 전부 실패하도록 본다.

인덱스와 쿼리 플랜 모델:
DB가 데이터를 어떻게 찾고 있는지 본다.

인증·인가 모델:
누구인지와 무엇을 할 수 있는지를 분리해서 본다.

비동기 처리 모델:
오래 걸리는 작업을 요청 흐름에서 분리한다.

캐시 일관성 모델:
빠른 응답과 최신 데이터 사이의 균형을 본다.

장애 전파 모델:
한 부분의 장애가 전체로 퍼지는 경로를 차단한다.

비용 구조 모델:
기능 하나가 사용자 증가에 따라 얼마의 비용을 만드는지 본다.

보안 위협 모델:
공격자가 시스템을 어떻게 악용할 수 있는지 먼저 생각한다.
```

최종적으로 중요한 사고는 다음입니다.

```text
기능이 동작하는가?
→ 데이터가 안전한가?
→ 권한이 올바른가?
→ 느려지지 않는가?
→ 장애에 버티는가?
→ 비용이 감당 가능한가?
→ 공격에 취약하지 않은가?
```

초급 개발자와 실무형 개발자의 차이는 여기에서 갈립니다.  
초급자는 “기능이 된다”에서 멈추고, 실무형 개발자는 “운영 가능한가”까지 봅니다.
