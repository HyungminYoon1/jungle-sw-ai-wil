## 4. 2-3W MVP 개발 기준

| 항목 | 팀 기준 |
|------|---------|
| Core Value First | 사용자가 우리 서비스를 써야 하는 단 하나의 이유를 먼저 구현 |
| Nice-to-Have | 댓글, 좋아요, 다크모드, 부가 설정처럼 핵심 검증과 무관한 기능은 뒤로 미룸 |
| 로그인/회원가입 | 핵심 기능 체험을 막는다면 비회원 흐름 또는 소셜 로그인 1개만 우선 검토 |
| 기술 리스크 Spike | AI 모델, RAG, VLM, 실시간 소켓, 외부 API처럼 실패 가능성이 큰 부분을 먼저 프로토타이핑 |
| 외부 의존성 | API rate limit, 비용, 응답 속도, 장애 시 fallback을 개발 초기에 확인 |
| 초기 배포 | 프로젝트 세팅 직후 Hello World 수준이라도 AWS 등 배포 환경에 올려 로컬/서버 차이를 빨리 확인 |
| CI/CD | main 또는 배포 브랜치 병합 시 테스트와 배포가 자동으로 이어지도록 GitHub Actions 등으로 구성 |
| 접속 환경 | HTTPS, 도메인, CORS, 환경 변수, DB 연결은 마지막 날이 아니라 MVP 초기에 검증 |
| Happy Path | 입력 -> AI 처리 -> 결과 확인 흐름이 끊기지 않아야 함 |
| 예외 처리 | AI 무응답, 네트워크 오류, 외부 API 오류, 빈 입력, 잘못된 입력에서 앱이 죽지 않고 안내해야 함 |

### MVP 완료 기준

- 핵심 사용자 흐름이 실제 배포 환경에서 동작한다.
- AI 기능이 서비스 핵심 가치와 직접 연결된다.
- AI 응답 지연 중 로딩 상태나 진행 상태가 보인다.
- 장애 상황에서 사용자에게 안내하고 복구 경로를 제공한다.
- 팀원이 본인이 작성하지 않은 주요 흐름도 말로 설명할 수 있다.
- 1차/2차 발표에서 구현된 기능은 데모로, 미완성 기능은 장표나 대체 화면으로 설명한다.
- 2차 발표 이후에는 가능하면 실제 런칭 또는 제한 공개를 시작해 고객 피드백을 수집한다.

## 5. 4-5W 폴리싱 기준

| 항목 | 팀 기준 |
|------|---------|
| Feature Freeze | 4W부터는 새 기능 추가를 멈추고 기존 핵심 흐름 안정화에 집중 |
| 안정성 | 시연 중 앱이 죽지 않도록 입력 검증, 예외 처리, fallback, 재시도 흐름을 강화 |
| 사용자 피드백 | 개발 지식이 없는 사용자 또는 타 팀 동료 5-10명에게 사용을 요청하고 설명 없이 관찰 |
| 정량 데이터 | 평균 AI 응답 대기 시간, 페이지 로딩 속도, 테스트 기간 처리 요청 수 등 발표에 쓸 수 있는 수치를 수집 |
| 정성 피드백 | 헷갈리는 버튼, 막히는 화면, 공유하고 싶은 결과, 기대와 다른 응답을 기록 |
| 개선 기록 | 사용자 피드백을 반영해 UI, 문구, 입력 흐름, 결과 화면을 바꾼 전후를 남김 |
| 코드 정리 | 디버깅용 `console.log`, 불필요한 로그, 임시 코드, 사용하지 않는 리소스를 제거 |
| 인프라 정리 | HTTPS, SSL 인증서, 도메인, CORS, DB, vector store, storage, 배포 상태를 재점검 |
| 건강 관리 | 발표 당일 컨디션을 위해 밤샘보다 밀도 있는 집중을 선택 |
| 장애 대응 | 버그가 생기면 책임 추궁보다 빠른 재현, 원인 분리, 우회, 복구를 우선 |

| 항목 | 기준 |
|------|------|
| GitHub Projects | 1W 기획, 2-3W MVP, 4-5W 폴리싱, 발표/포스터/영상, 인프라, 사용자 테스트로 보드를 나눔 |
| Issue 단위 | 사용자 흐름, AI 기능, 데이터 파이프라인, 배포, 테스트, 발표 산출물 단위로 작게 관리 |
| Branch 전략 | `main`은 발표 가능한 안정 브랜치로 유지하고, 기능은 `feature/*`, 수정은 `fix/*`, 문서는 `docs/*`에서 작업 |
| PR 기준 | 목적, 변경 범위, 테스트 결과, 배포 영향, 환경 변수 추가 여부, 스크린샷/데모 링크를 포함 |
| 머지 기준 | 핵심 흐름 동작, 관련 테스트 또는 수동 검증 완료, 비밀값 미포함, 최소 1명 리뷰 |
| Commit | 기능, 버그 수정, 문서, 인프라 변경을 의미 있는 단위로 나누어 기록 |
| README | 서비스 개요, 핵심 기능, 아키텍처, AI 구조, 실행 방법, 환경 변수 이름, 배포 주소, 데모, 회고를 포함 |
| Decision Log | 주제, 기술 스택, 아키텍처, 외부 API, 모델, 배포 방식처럼 되돌리기 어려운 결정은 이유와 대안을 함께 남김 |

## 13. 보안 / 비용 규칙

- `.env`, API key, DB password, OAuth secret, AWS credential은 저장소, 로그, 슬랙, 발표자료, 포스터, 영상에 노출하지 않는다.
- credential 확인이 필요하면 값이 아니라 존재 여부와 환경 변수 이름만 공유한다.
- 로그를 공유할 때는 token, key, password, email, 개인 식별 정보, 내부 URL을 마스킹한다.
- OpenAI, Bedrock, 외부 API, DB, vector store, storage 비용 이상 징후는 즉시 공유한다.
- 사용하지 않는 EC2, DB, vector store, storage, 배포 인스턴스는 종료 계획을 세운다.
- 배포 환경의 HTTPS, SSL 인증서 만료, CORS, rate limit을 발표 전 다시 확인한다.
- 발표 자료와 README에는 실제 비밀값 대신 `.env.example` 또는 환경 변수 이름만 적는다.

## 14. 완료 기준

- MVP 핵심 흐름이 배포 환경에서 시작부터 끝까지 동작한다.
- AI 기능이 단순 호출이 아니라 서비스 가치와 기술적 챌린지를 보여준다.
- 장애, 지연, 빈 입력, 잘못된 입력, 외부 API 실패 상황에서 사용자 안내가 있다.
- 주간 진행상황과 멘토링 피드백이 누적되어 있고, 반영 여부를 설명할 수 있다.
- 사용자 테스트 결과와 개선 사례가 발표 자료에 들어갈 수 있게 정리되어 있다.
- 최종 발표 7분 흐름, 백업 영상, 포스터, 발표 영상, README, WIL이 준비되어 있다.
- 모든 팀원이 본인이 맡지 않은 핵심 아키텍처와 AI 흐름도 말로 설명할 수 있다.
