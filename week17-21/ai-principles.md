# AI 활용 원칙 (Week 17-21)

> 작성 시점: Week 17 시작 시
>
> 프로젝트: 나만의 무기를 갖기
>
> 기준 기간: 2026-06-19 ~ 2026-07-25
>
> 이번 기간은 AI-native 서비스를 만드는 팀 프로젝트다. AI 사용은 적극 허용하되, AI가 만든 결과를 이해하지 못한 상태로 제출하거나 발표하지 않는다. 모든 팀원은 본인이 개발하지 않은 핵심 흐름도 말로 설명할 수 있어야 한다.

---

## 1. 이번 기간 AI 사용 수준

| 수준 | 허용 | 선택 |
|------|------|:----:|
| 일부 사용 | 개념 학습, 공식 문서 이해, 오류 메시지 해석 | ☑ |
| 학습 보조 | 위 + 설계 검토, 코드 리뷰, 테스트 시나리오 작성, 발표 구조 점검 | ☑ |
| 코드 생성 | 코드 초안, boilerplate, 반복 작업, 리팩터링 보조, 문서 초안 작성 | ☑ |
| 제품 검증 보조 | 사용자 흐름 점검, UX 문구 개선, 데모 시나리오, 발표 스토리라인 점검 | ☑ |

나만무는 AI 활용 능력 자체를 보여줘야 하는 프로젝트이므로 AI를 적극적으로 사용한다. 다만 AI 사용의 목적은 빠른 산출이 아니라, 더 좋은 문제 정의, 더 빠른 기술 리스크 검증, 더 설명 가능한 구현, 더 안정적인 발표 준비에 둔다.

---

## 2. 허용하는 것

- 주제 후보 발산, 사용자 문제 정의, AI-native 여부 점검
- MVP 범위 축소, nice-to-have 기능 분리, 발표 스토리라인 검토
- 기술 스택 후보 비교와 선택 근거 정리
- RAG, VLM, fine-tuning, multi-agent, streaming, guardrail 등 AI 기능 설계 검토
- API, DB schema, 데이터 파이프라인, 아키텍처 초안 작성 보조
- 코드 초안, boilerplate, 테스트 코드, 리팩터링 후보 생성
- 오류 메시지 분석, 장애 원인 후보 정리, 디버깅 절차 제안
- UX 문구, 로딩/오류 안내 문구, 사용자 테스트 질문지 작성
- README, 주간 진행상황, 멘토링 자료, 발표 자료, 포스터 문구 초안 작성
- 발표 리허설 질문, Q&A 예상 질문, 기술적 챌린지 설명 점검

---

## 3. 허용하지 않는 것

- 설명할 수 없는 AI 생성 코드를 그대로 반영하거나 제출하기
- AI가 만든 기획을 팀 검토 없이 프로젝트 주제로 확정하기
- 단순 ChatGPT wrapper를 AI-native 서비스처럼 포장하기
- RAG/MCP/Agent/VLM 같은 용어를 실제 구현 또는 검증 없이 발표자료에 넣기
- AI 응답을 사실 검증 없이 사용자에게 최종 결과로 제공하기
- API key, DB password, OAuth secret, AWS credential, Personal Access Token, `.env` 값을 AI 대화나 로그에 노출하기
- 비용 한도 없이 OpenAI, Bedrock, 외부 API, vector DB 호출을 반복 실행하기
- 모델 출력이 마음에 든다는 이유만으로 hallucination, latency, fallback 검증을 생략하기
- 사용자 테스트 결과를 AI가 임의로 꾸며내거나 과장하기
- 팀원이 이해하지 못한 구조를 발표 담당자에게만 맡기기

## 4. 필수 검증 기준

AI 도움을 받은 산출물은 아래 항목을 확인한 뒤 완료로 본다.

| 구분 | 검증 기준 |
|------|-----------|
| 기획 | AI가 핵심 가치인지, 단순 wrapper가 아닌지, 5주 안에 MVP가 가능한지 팀이 직접 판단 |
| 설계 | 아키텍처, 데이터 흐름, AI 처리 흐름, 실패 케이스를 팀원이 설명 가능 |
| 코드 | 실행, 테스트 또는 수동 검증을 통과하고, 주요 함수의 책임과 한계를 설명 가능 |
| RAG | 데이터 출처, chunking, embedding, retrieval, citation 또는 근거 표시 방식을 확인 |
| Agent | tool 목록, 선택 이유, 상태 관리, 종료 조건, 반복 제한, 실패 복구 흐름을 확인 |
| VLM/멀티모달 | 입력 제약, 전처리, 실패 케이스, 응답 지연 UX를 확인 |
| LLM 응답 | hallucination 방지, timeout, streaming, fallback, 금칙어/빈 입력 방어를 확인 |
| 사용자 경험 | 사용자가 결과를 이해하고 검토할 수 있는지 화면 기준으로 확인 |
| 보안 | 비밀값 미노출, `.env` 미커밋, 최소 권한, 로그 마스킹 확인 |
| 비용 | 호출량, rate limit, 예상 비용, 미사용 리소스 종료 여부 확인 |

## 5. 비밀값과 로그 원칙

- `.env` 파일 내용은 출력하지 않는다.
- credential 확인이 필요하면 값이 아니라 존재 여부와 환경 변수 이름만 확인한다.
- 로그에는 API key, token, password, connection string, 개인 식별 정보를 남기지 않는다.
- README, WIL, 발표자료, 포스터, 영상에는 실제 비밀값 대신 환경 변수 이름만 적는다.
- AI 대화에 실제 고객 데이터, 민감한 사용자 입력, 내부 URL, private key를 그대로 붙여 넣지 않는다.
- 배포 또는 클라우드 실습 후 사용하지 않는 EC2, DB, storage, vector store, 배포 인스턴스는 종료 계획을 세운다.

## 6. 프로젝트 단계별 AI 활용 기준

### 1W - 주제 선정 / 기획

- AI를 아이디어 발산과 반례 찾기에 사용한다.
- 주제 선정은 팀이 직접 결정하고, AI가 만든 표현을 그대로 발표하지 않는다.
- AI가 핵심 가치인지, UI로 보여줄 수 있는지, 기술적 챌린지가 있는지 검토한다.
- 유사 서비스나 유사 팀 주제가 있다면 차별화 포인트를 사람이 직접 정리한다.

### 2-3W - MVP 개발

- AI를 기술 리스크 spike, boilerplate, 테스트 케이스, 오류 분석에 적극 활용한다.
- 핵심 기능은 입력 -> AI 처리 -> 결과 확인 흐름이 실제로 동작해야 한다.
- AI 응답 품질은 문장 자연스러움과 근거 검증 가능성을 분리해 평가한다.
- 소형 모델, RAG, 고성능 모델, prompt engineering의 장단점을 비용과 품질 기준으로 비교한다.

### 4-5W - 폴리싱 / 발표 준비

- AI를 UX 문구, 오류 안내, 발표 스토리라인, Q&A 예상 질문 작성에 활용한다.
- 새 기능 생성보다 안정화, 예외 처리, 사용자 테스트 결과 정리에 집중한다.
- 발표자료에는 실제 동작하는 것과 후속 확장 계획을 구분해서 적는다.
- 시연 실패에 대비해 백업 영상과 대체 설명 자료를 준비한다.

---

## 7. 이번 기간 AI 활용 목표

- AI를 빠른 구현 도구로만 쓰지 않고, 문제 정의와 기술 리스크 검증을 돕는 도구로 사용한다.
- 팀원이 설명할 수 없는 구조는 프로젝트 핵심 구조로 채택하지 않는다.
- AI 기능은 "그럴듯한 답변"보다 "사용자가 검토할 수 있는 결과"를 기준으로 만든다.
- 모델 성능, RAG 품질, 응답 지연, 비용, 보안, 사용자 경험을 함께 평가한다.
- 최종 발표에서는 AI를 어떻게 썼는지보다, AI를 통해 어떤 사용자 문제를 해결했고 어떤 기술적 챌린지를 넘었는지를 설명한다.
