# AI 활용 원칙 (Week 11-12)

## 과제별 AI 사용 범위

| 과제 | AI 사용 | 필수 조건 |
|------|---------|-----------|
| **PintOS Project 3 - Virtual Memory** | 학습·검토 보조 중심 | SPT, page fault, lazy loading, stack growth, mmap, swap 흐름을 직접 설명할 수 있어야 함 |
| **공통 모듈 설계** | 제한적 허용 | 팀이 먼저 필요한 함수, 호출 위치, 실패 처리 정책을 합의한 뒤 AI는 누락 검토에만 사용 |
| **테스트 실패 분석** | 허용 | 실패 로그 해석, 의심 코드 경로, 재현 순서 정리에 활용하되 수정 내용은 직접 검증 |
| **주간 공유 발표 / WIL** | 허용 | 구현 내용과 트러블슈팅을 과장 없이 정리 |
| **퀴즈 / 제한 환경 실습** | 미허용 | AI·인터넷 사용 제한 환경 가정 |

## 우리 팀 선택 (PintOS Project 3)

| 수준 | 허용 | 선택 |
|------|------|------|
| 일부 사용 | 공식 문서 이해, 용어 정리, 오류 메시지 해석 | □ |
| 학습 보조 | 위 + 테스트 실패 원인 분석, 디버깅 방향, 코드 리뷰 관점 정리 | ☑ |
| 코드 생성 | 위 + 핵심 구현 코드 생성 | □ |

이번 주에는 10주차 회고를 반영해 AI를 코드 생성기처럼 사용하지 않는다. 특히 팀 공통 모듈을 AI가 먼저 크게 생성하는 방식은 피하고, 사람이 먼저 최소 구조를 합의한 뒤 AI는 검토 보조로 사용한다.

## 핵심 원칙

- AI가 설명한 내용은 반드시 KAIST PintOS 문서, 코드, 테스트 결과와 대조한다.
- `supplemental page table`, `vm_try_handle_fault()`, lazy loading, stack growth, frame eviction, swap, `mmap/munmap` 핵심 구현은 이해 없이 복사하지 않는다.
- 공통 helper를 만들기 전에는 팀이 먼저 "어떤 함수가 필요한지", "누가 호출하는지", "실패 시 무엇을 반환하거나 정리하는지"를 합의한다.
- AI가 제안한 공통 구조가 과도하면 줄이고, 현재 테스트와 구현 단계에 필요한 최소 범위만 남긴다.
- 테스트 통과 여부보다 왜 통과했는지, 어떤 page lifecycle과 자원 정리를 검증했는지 설명할 수 있어야 한다.
- 퀴즈나 제한 환경에서는 AI를 사용하지 않는다.

## 허용하는 것

- KAIST PintOS Project 3 문서, FAQ, Appendix 개념 요약 요청
- SPT, page fault handler, lazy loading, stack growth, mmap, swap 흐름 설명 요청
- `pt-*`, `page-*`, `mmap-*`, `lazy-*`, `swap-*` 실패 로그 해석과 의심 코드 경로 정리
- PR 리뷰 체크리스트 작성 보조
- 구현 후 코드 흐름을 설명해 보고 빈틈을 찾는 질문 생성
- 발표 자료, WIL, 블로그 문장 정리 보조

## 허용하지 않는 것

- Project 3 핵심 구현 코드를 이해 없이 AI로 생성해 그대로 붙여 넣기
- 팀 합의 전 AI에게 공통 VM skeleton이나 helper 묶음을 크게 생성하도록 지시하기
- 테스트 실패 원인을 확인하지 않고 AI가 제안한 수정만 적용하기
- 설명할 수 없는 page fault, SPT, swap, mmap 코드를 main branch에 병합하기
- 퀴즈 또는 제한 환경에서 AI 사용하기

## 예외 상황

- Docker, Ubuntu 22.04, 빌드 도구, 테스트 실행 명령처럼 환경 설정 문제는 AI 도움을 받을 수 있다.
- 문서나 발표 자료를 정리할 때는 AI 도움을 받을 수 있지만, 구현 성과와 이해 수준을 과장하지 않는다.
- 마감 직전이라도 핵심 VM 구현 코드를 이해 없이 병합하지 않는다.
