## 1. Project 2는 무엇을 하는 과제인가

Project 1에서는 커널 내부의 스레드, 스케줄러, 동기화가 중심이었다. 테스트도 커널 안에서 직접 실행되는 형태였다.

Project 2부터는 사용자 프로그램을 실행한다. 사용자 프로그램은 커널과 같은 권한을 갖지 않는다. 파일을 열고 싶거나, 화면에 출력하고 싶거나, 다른 프로그램을 실행하고 싶으면 커널에 요청해야 한다. 이 요청 통로가 system call이다.

Project 2의 핵심은 다음 문장으로 정리할 수 있다.

> 커널이 사용자 프로그램을 안전하게 실행시키고, 사용자 프로그램의 요청을 system call로 받아 처리하게 만든다.

여기서 중요한 단어는 "안전하게"다. 사용자 프로그램은 잘못된 포인터를 넘길 수 있고, 존재하지 않는 파일을 열려고 할 수 있고, 자식 프로세스를 기다리는 순서를 이상하게 만들 수도 있다. 그래도 커널은 panic을 내거나 멈추면 안 된다. 문제가 있는 사용자 프로세스만 종료하고, 커널은 계속 살아 있어야 한다.

원본 introduction의 background를 더 쉽게 풀면 이렇다. 기본 PintOS는 이미 사용자 프로그램을 파일에서 읽어 메모리에 올리고 실행하는 뼈대를 가지고 있다. 하지만 그 프로그램이 화면에 출력하거나, 파일을 열거나, 부모가 `wait`로 자식의 종료 상태를 회수하는 상호작용은 아직 제대로 할 수 없다. Project 2는 이 빈 부분을 system call과 process 관리로 채우는 과제다.

또한 Project 2는 `userprog` 디렉터리만 보면 끝나는 과제가 아니다. 실행 파일을 읽으려면 file system을 써야 하고, 여러 프로세스가 동시에 움직이면 thread와 synchronization이 필요하며, 잘못된 주소 접근은 exception/page fault와 연결된다. 그리고 누적형 과제이기 때문에 Project 1에서 만든 thread 기능과 테스트도 계속 유지되어야 한다.

## 2. 커널, 스레드, 프로세스, 사용자 프로그램

처음에는 용어가 헷갈리기 쉽다. Project 2에서는 아래 네 개를 구분해야 한다.

| 개념 | 의미 |
|---|---|
| kernel | 하드웨어와 자원을 관리하는 운영체제 본체 |
| thread | CPU에서 실행되는 실행 흐름 |
| process | 사용자 프로그램 실행 단위 |
| user program | 커널 위에서 실행되는 일반 프로그램 |

PintOS Project 2에서는 한 프로세스가 하나의 스레드를 가진다고 보면 된다. 멀티스레드 사용자 프로세스는 다루지 않는다. 즉, 사용자 프로그램 하나를 실행하면 그 프로그램을 담당하는 커널 스레드가 하나 생기고, 그 스레드가 사용자 모드로 내려가 프로그램 코드를 실행한다.

따라서 Project 1에서 배운 thread 지식은 그대로 필요하다. 프로세스가 새로 생기거나, 잠들거나, 기다리거나, 종료되는 일은 결국 thread의 생성, block, unblock, exit와 연결된다.

## 3. 사용자 프로그램 실행 흐름 한눈에 보기

사용자가 PintOS에서 다음과 같은 명령을 실행한다고 생각해 보자.

```text
run 'args-single onearg'
```

커널 내부에서는 대략 다음 흐름이 일어난다.

```text
1. 커널이 실행할 명령줄을 받는다.
2. 명령줄에서 프로그램 이름과 인자를 분리한다.
3. 파일 시스템에서 실행 파일을 찾는다.
4. ELF loader가 실행 파일을 메모리에 올린다.
5. 사용자 스택을 만들고 argc, argv가 보이도록 인자를 배치한다.
6. CPU가 user mode에서 프로그램의 시작점으로 진입한다.
7. 사용자 프로그램이 실행된다.
8. 사용자 프로그램이 파일 입출력이나 종료를 원하면 system call을 호출한다.
9. CPU가 kernel mode로 전환된다.
10. syscall handler가 요청 번호와 인자를 읽는다.
11. 커널이 포인터, 파일 디스크립터, 프로세스 관계를 검증한다.
12. 요청을 처리하고 결과를 사용자 프로그램에 돌려준다.
13. 프로그램이 exit하거나 예외가 나면 프로세스를 정리한다.
```

여기서 한 가지 전제가 있다. 사용자 프로그램은 PintOS 파일 시스템 안에 들어 있어야 실행할 수 있다. 테스트 스크립트는 보통 이 과정을 자동으로 처리하지만, 직접 실행할 때는 `pintos -p ... -- run ...`처럼 프로그램 파일을 PintOS 파일 시스템에 복사한 뒤 실행하는 흐름을 이해해 두면 디버깅에 도움이 된다.

Project 2의 각 구현 과제는 이 흐름 중 비어 있는 부분을 채우는 일이다.

## 4. User Mode와 Kernel Mode

운영체제는 사용자 프로그램을 믿지 않는다. 사용자 프로그램이 커널 메모리를 마음대로 읽거나 쓰게 하면 한 프로그램의 버그가 전체 운영체제를 망가뜨릴 수 있다.

그래서 CPU는 권한 수준을 나눈다.

| 모드 | 할 수 있는 일 |
|---|---|
| user mode | 사용자 프로그램 실행, 제한된 메모리 접근 |
| kernel mode | 커널 코드 실행, 하드웨어와 커널 메모리 접근 |

사용자 프로그램은 user mode에서 실행된다. 파일 시스템 접근, 프로세스 생성, 종료 상태 전달 같은 작업은 직접 할 수 없다. 대신 system call을 호출해서 커널에게 요청한다. system call이 발생하면 CPU는 kernel mode로 전환되고, 커널의 syscall handler가 실행된다.

이 구조 때문에 system call은 Project 2의 중심이다. 사용자 프로그램이 커널을 사용하는 유일한 공식 문이라고 볼 수 있다.

## 5. ELF Loader와 프로그램이 메모리에 올라가는 과정

사용자 프로그램은 실행 파일 형태로 파일 시스템 안에 들어 있다. PintOS는 ELF 형식의 실행 파일을 읽을 수 있다. ELF는 실행 파일 안에 코드, 데이터, BSS 같은 세그먼트 정보를 담고 있는 형식이다.

실행 파일을 실행한다는 것은 단순히 파일을 여는 것이 아니다. 커널은 실행 파일을 읽고, 그 안의 세그먼트를 사용자 가상 메모리에 배치해야 한다. 코드 세그먼트는 실행될 명령어를 담고, 데이터 세그먼트는 초기화된 전역 변수 등을 담는다.

여기서 segment는 실행 파일 안의 큰 덩어리라고 생각하면 된다. 예를 들어 code segment에는 CPU가 실행할 명령어가 들어 있고, initialized data segment에는 처음부터 값이 정해진 전역 데이터가 들어 있으며, BSS에는 초기값이 0인 데이터가 놓인다.

초심자는 다음 그림을 먼저 기억하면 된다. 주소는 아래로 갈수록 낮아지고, 위로 갈수록 높아진다.

```text
사용자 가상 주소 공간

높은 주소
USER_STACK +----------------------------------+
           | user stack                       |
           | 함수 호출, 지역 정보, 인자 정보 |
           | 아래 방향으로 자람              |
           |                v                 |
           |                                  |
           | 비어 있는 영역                  |
           |                                  |
           |                ^                 |
           | data/BSS 위쪽의 빈 영역         |
           +----------------------------------+
           | BSS                              |
           | 초기값이 0인 전역/정적 데이터   |
           +----------------------------------+
           | initialized data                 |
           | 초기값이 있는 전역/정적 데이터  |
           +----------------------------------+
           | code segment                     |
0x400000   | 실행할 기계어 명령어             |
           +----------------------------------+
낮은 주소
```

Project 2에서는 `load()` 계열 코드가 실행 파일을 읽어 메모리에 올리고, `setup_stack()` 계열 코드가 사용자 스택을 준비한다. 특강 전에는 함수 이름을 외우기보다, "실행 파일을 메모리에 올리는 단계"와 "프로그램 시작 시 필요한 스택을 만드는 단계"가 분리되어 있다는 점을 이해하면 충분하다.

원본 문서의 typical memory layout에서 중요한 포인트는 세 가지다.

- code segment는 낮은 주소 쪽에 있으며, PintOS 문서 기준으로 사용자 가상 주소 `0x400000` 근처에서 시작한다.
- user stack은 높은 주소인 `USER_STACK`에서 시작하고, 함수 호출이나 인자 저장이 일어나면서 아래 방향으로 자란다.
- data/BSS 위쪽의 빈 영역은 이후 확장될 수 있지만, Project 2에서는 사용자 프로그램용 heap 확장을 구현하지 않는다.
- Project 2에서는 사용자 스택 크기를 고정된 크기로 다루며, stack growth는 Project 3에서 더 본격적으로 다룬다.

## 6. 가상 주소와 페이지 테이블을 왜 알아야 하는가

Project 2 본문은 시작하기 전에 appendix의 동기화와 가상 주소를 읽으라고 권한다. 그 이유는 user program 구현이 주소 검증과 강하게 연결되기 때문이다.

PintOS의 가상 주소 공간은 크게 둘로 나뉜다.

| 영역 | 의미 |
|---|---|
| user virtual memory | 사용자 프로세스가 접근할 수 있는 영역 |
| kernel virtual memory | 커널만 접근해야 하는 영역 |

경계는 `KERN_BASE`다. 사용자 주소는 `KERN_BASE`보다 아래에 있어야 한다. `is_user_vaddr()` 같은 도구는 이 경계를 확인할 때 사용된다.

이 구조를 그림으로 보면 다음과 같다.

```text
낮은 주소                                               높은 주소
0                         KERN_BASE
+-------------------------+-----------------------------+
| user virtual memory     | kernel virtual memory       |
| 프로세스마다 달라짐     | 모든 프로세스에서 공통     |
+-------------------------+-----------------------------+
```

중요한 차이는 "프로세스마다 달라지는가"다. 사용자 가상 메모리는 프로세스마다 독립적이다. A 프로세스의 주소 `0x400000`과 B 프로세스의 주소 `0x400000`은 같은 숫자처럼 보여도 서로 다른 메모리를 가리킬 수 있다. 커널이 다른 프로세스로 context switch할 때는 활성 page table도 바뀌기 때문이다.

반대로 kernel virtual memory는 전역적이다. 어떤 사용자 프로세스가 실행 중이든 커널 영역은 같은 방식으로 보인다. 그래서 커널 코드는 공통 커널 자료구조와 하드웨어 자원에 접근할 수 있다.

하지만 주소가 user 영역에 있다는 것만으로 충분하지 않다. 그 주소가 실제 물리 메모리에 매핑되어 있는지도 확인해야 한다. 이때 필요한 배경이 page table이다.

PintOS의 페이지 테이블은 `pml4`라는 구조로 다뤄진다. 개념적으로는 다음 질문에 답한다.

```text
이 사용자 가상 주소가 실제 메모리 프레임에 연결되어 있는가?
```

예를 들어 사용자 프로그램이 `write(1, buffer, size)`를 호출하면, 커널은 `buffer`가 가리키는 메모리를 읽어야 한다. 이때 `buffer`가 다음과 같으면 문제가 된다.

- null pointer
- kernel address
- 매핑되지 않은 user address
- 시작 주소는 유효하지만 중간에 page boundary를 넘어가며 invalid page에 걸치는 buffer

이런 주소를 커널이 그대로 믿고 읽으면 커널이 page fault를 내거나, 더 나쁘게는 커널 메모리를 잘못 건드릴 수 있다. 그래서 Project 2에서는 user pointer validation이 매우 중요하다.

정리하면 virtual memory layout을 볼 때는 다음 질문을 던지면 된다.

- 이 주소는 `KERN_BASE`보다 아래인가, 위인가?
- 아래라면 현재 프로세스의 user page table에 실제로 매핑되어 있는가?
- 커널이 이 주소를 읽거나 쓸 때 실패하면, 잡고 있던 lock과 할당한 메모리를 정리할 수 있는가?

## 7. Argument Passing

사용자 프로그램은 보통 `main(int argc, char *argv[])` 형태로 시작한다. 따라서 커널은 프로그램을 시작하기 전에 `argc`와 `argv`가 사용자 프로그램에서 보이도록 준비해야 한다.

조금 더 정확히 말하면, 사용자 프로그램은 곧바로 `main()`에서 시작하지 않는다. PintOS 사용자 라이브러리에는 `_start()`라는 시작 함수가 있고, 이 함수가 `main(argc, argv)`를 호출한다. 그리고 `main()`이 값을 반환하면 `_start()`가 그 값을 `exit()`에 넘겨 프로세스를 종료한다. 따라서 커널이 `argc`와 `argv`를 제대로 준비하지 못하면, 사용자 프로그램은 `main()`에 들어가기도 전에 잘못된 스택을 읽다가 page fault를 낼 수 있다.

예를 들어 다음 명령을 실행한다고 하자.

```text
grep foo bar
```

사용자 프로그램 입장에서는 다음처럼 보여야 한다.

```text
argc = 3
argv[0] = "grep"
argv[1] = "foo"
argv[2] = "bar"
argv[3] = NULL
```

이 값을 사용자 프로그램이 읽을 수 있으려면 문자열과 포인터 배열이 사용자 스택에 놓여 있어야 한다. x86-64 호출 규약에 따라 첫 번째 인자 `argc`는 `%rdi`, 두 번째 인자 `argv`는 `%rsi`로 전달된다.

초심자가 여기서 잡아야 할 핵심은 다음이다.

- 명령줄 문자열을 공백 기준으로 토큰화한다.
- 문자열 자체를 사용자 스택에 복사한다.
- 각 문자열의 주소를 `argv` 배열처럼 다시 스택에 넣는다.
- `argv[argc]`는 `NULL`이어야 한다.
- 스택 정렬과 가짜 return address도 맞춰야 한다.

예를 들어 `/bin/ls -l foo bar`를 실행한다고 하자. 커널은 이 명령줄을 다음 네 단어로 나눠야 한다.

```text
/bin/ls
-l
foo
bar
```

이후 사용자 스택에는 크게 두 종류의 값이 들어간다.

- 문자열 자체: `"/bin/ls\0"`, `"-l\0"`, `"foo\0"`, `"bar\0"`
- 문자열을 가리키는 주소들: `argv[0]`, `argv[1]`, `argv[2]`, `argv[3]`

문자열과 주소를 둘 다 넣는 이유는 C 프로그램이 `argv[1]`처럼 포인터 배열을 통해 인자 문자열에 접근하기 때문이다. `argv[1]`에는 `"-l"`이라는 글자 자체가 들어 있는 것이 아니라, `"-l"` 문자열이 놓인 주소가 들어 있다.

개념적인 스택 모양은 다음과 같다. 실제 주소값은 실행 상황에 따라 다를 수 있지만, 배치 의도는 이렇다.

```text
높은 주소
+-----------------------------+
| "bar\0"                     |  문자열들
| "foo\0"                     |
| "-l\0"                      |
| "/bin/ls\0"                 |
+-----------------------------+
| padding                     |  8바이트 정렬을 맞추기 위한 빈 공간
+-----------------------------+
| NULL                        |  argv[4], argv의 끝 표시
| &"bar\0"                    |  argv[3]
| &"foo\0"                    |  argv[2]
| &"-l\0"                     |  argv[1]
| &"/bin/ls\0"                |  argv[0]
+-----------------------------+
| fake return address = 0     |
+-----------------------------+ <- 초기 stack pointer
낮은 주소

레지스터:
RDI = argc = 4
RSI = argv 배열의 시작 주소, 즉 argv[0] 슬롯의 주소
```

여기서 `argv[argc] == NULL`은 배열의 끝을 알려 주는 표식이다. C 코드가 `argv`를 순회할 때 어디서 멈춰야 하는지 알 수 있게 해 준다. 8바이트 정렬은 x86-64에서 주소와 포인터를 자연스럽게 다루기 위한 약속에 가깝다. fake return address는 `_start()`가 일반 함수 호출을 받은 것처럼 스택 모양을 맞추기 위한 자리다. 실제로 `_start()`가 반환될 것을 기대하는 것은 아니다.

인자 전달을 구현할 때는 여러 공백을 하나의 공백처럼 처리해야 한다. 예를 들어 `grep   foo   bar`도 `grep foo bar`와 같은 인자 배열로 해석되어야 한다. 원본 문서는 `strtok_r()` 같은 재진입 가능한 문자열 토큰화 함수를 참고할 수 있다고 설명한다.

argument passing을 디버깅할 때는 `hex_dump()`가 유용할 수 있다. 스택에 문자열, 포인터, 정렬용 padding, fake return address가 의도한 순서로 들어갔는지 눈으로 확인할 수 있기 때문이다. 단, 최종 제출 코드에는 불필요한 디버그 출력이 남지 않도록 해야 한다.

argument passing이 제대로 되지 않으면 `args-*` 테스트가 실패한다. 사용자 프로그램이 시작은 되었지만, `main()`이 기대하는 인자를 보지 못하기 때문이다.

## 8. System Call

system call은 사용자 프로그램이 커널 기능을 요청하는 방법이다. 사용자 프로그램은 직접 파일 시스템 함수나 커널 함수를 호출할 수 없다. 대신 사용자 라이브러리의 system call wrapper를 통해 CPU의 `syscall` 명령을 실행한다.

x86-64 PintOS에서 system call 번호와 인자는 레지스터로 전달된다.

| 값 | 위치 |
|---|---|
| system call number | `%rax` |
| 1번째 인자 | `%rdi` |
| 2번째 인자 | `%rsi` |
| 3번째 인자 | `%rdx` |
| 4번째 인자 | `%r10` |
| 5번째 인자 | `%r8` |
| 6번째 인자 | `%r9` |

커널의 syscall handler는 `struct intr_frame`을 통해 이 레지스터 값을 읽는다. 반환값이 있는 system call은 결과를 다시 `%rax`에 넣어 사용자 프로그램으로 돌려준다.

여기서 초심자가 헷갈리기 쉬운 점이 있다. syscall 번호나 정수 인자는 레지스터에서 바로 읽을 수 있다. 하지만 인자가 포인터라면 이야기가 다르다. 레지스터에 들어 있는 값은 "사용자 메모리의 주소"일 뿐이고, 그 주소가 가리키는 실제 데이터는 커널이 별도로 읽어야 한다. 이때 user pointer validation이 필요하다.

Project 2에서 구현해야 하는 system call은 크게 세 묶음으로 볼 수 있다.

| 묶음 | 예시 | 핵심 |
|---|---|---|
| 종료와 실행 | `halt`, `exit`, `fork`, `exec`, `wait` | 프로세스 생명주기 |
| 파일 생성과 열기 | `create`, `remove`, `open`, `close` | 파일 시스템 진입 |
| 파일 입출력 | `read`, `write`, `filesize`, `seek`, `tell` | fd와 buffer 검증 |

system call 구현에서 가장 중요한 태도는 "사용자 입력을 신뢰하지 않는 것"이다. system call 번호가 이상할 수 있고, fd가 잘못되었을 수 있고, 포인터가 잘못되었을 수 있다. 이런 경우에도 커널 전체가 무너지면 안 된다.

`halt`는 PintOS 전체를 종료하는 system call이므로 일반적인 테스트 흐름에서 자주 쓰는 기능이 아니다. 원본 문서도 deadlock 상황 같은 정보를 잃을 수 있으므로 거의 사용하지 말라고 설명한다. 보통은 `exit`, 파일 관련 syscall, process control syscall의 동작을 먼저 안정화하는 것이 중요하다.

## 9. User Pointer Validation

Project 2에서 커널은 사용자 프로그램이 넘긴 포인터를 자주 읽는다.

포인터는 "값이 들어 있는 곳"이 아니라 "값이 있는 주소"다. 예를 들어 `write(fd, buffer, size)`에서 `buffer`는 출력할 문자열 자체가 아니라, 문자열이 놓여 있는 사용자 메모리 주소다. 커널은 그 주소를 따라가서 데이터를 읽어야 한다. 문제는 사용자 프로그램이 일부러 또는 실수로 잘못된 주소를 넘길 수 있다는 점이다.

예를 들어 다음 system call을 보자.

```text
write(fd, buffer, size)
```

여기서 `buffer`는 사용자 가상 주소다. 커널 주소가 아니다. 커널은 이 주소가 안전한지 확인한 뒤에만 읽어야 한다.

검증할 때 생각해야 하는 질문은 다음과 같다.

- 포인터가 null인가?
- 주소가 user 영역인가?
- 해당 주소가 page table에 매핑되어 있는가?
- buffer가 여러 page에 걸칠 때 모든 page가 유효한가?
- 문자열 인자라면 null terminator를 만날 때까지 안전하게 읽을 수 있는가?
- 검증 중 실패하면 이미 획득한 lock이나 할당한 메모리를 정리하는가?

공식 문서는 두 가지 접근을 설명한다.

| 방식 | 의미 |
|---|---|
| 사전 검증 | 포인터를 역참조하기 전에 user address와 page mapping을 확인 |
| page fault 활용 | user 영역 여부만 확인하고 접근하다가 fault를 처리 |

초심자에게는 사전 검증 방식이 이해하기 쉽다. 잘못된 주소를 발견하는 지점과 자원을 정리하는 지점이 비교적 명확하기 때문이다.

여기서 appendix의 `04_virtual_address.md`와 `05_page_table.md`가 필요하다. `is_user_vaddr()`는 주소 범위를 보는 도구이고, `pml4_get_page()` 같은 page table 관련 함수는 실제 매핑 여부를 확인하는 데 연결된다.

여기서 page는 메모리를 일정한 크기로 나눈 단위라고 생각하면 된다. 어떤 주소가 user 영역에 있더라도, 그 주소가 속한 page가 실제 메모리에 연결되어 있지 않으면 접근할 수 없다. 이때 발생하는 예외가 page fault다. Project 2에서는 page fault가 "무조건 커널 버그"라는 뜻은 아니다. 사용자 프로그램이 잘못된 주소를 넘겼을 때도 page fault가 날 수 있으며, 이 경우 커널은 전체 시스템을 멈추는 대신 해당 사용자 프로세스만 정리해야 한다.

## 10. File Descriptor

사용자 프로그램은 파일을 직접 가리키는 `struct file *`를 알면 안 된다. 대신 정수 번호를 받는다. 이 번호가 file descriptor, 줄여서 fd다.

| fd | 의미 |
|---|---|
| 0 | standard input |
| 1 | standard output |
| 2 이상 | 열린 파일 |

`open()`은 파일을 열고 fd를 반환한다. 이후 사용자 프로그램은 그 fd를 `read`, `write`, `seek`, `tell`, `close`에 넘긴다.

커널은 프로세스마다 fd table을 관리해야 한다. 한 프로세스의 fd 3과 다른 프로세스의 fd 3은 같은 의미가 아닐 수 있다. 각 프로세스는 독립적인 fd 집합을 가진다.

기본 Project 2에서는 fd 0과 fd 1이 콘솔용으로 예약되어 있고, `open()`은 이 둘을 반환하지 않는다. 반면 extra 요구사항까지 구현할 경우에는 Linux처럼 `stdin`, `stdout`을 닫을 수 있어야 한다. 닫힌 0번 또는 1번 fd는 이후 `open()`이나 `dup2()`를 통해 다시 사용될 수 있다.

fd를 이해할 때 중요한 점은 다음이다.

- fd는 사용자에게 보여 주는 번호다.
- 실제 파일 객체는 커널 안에 있다.
- 잘못된 fd가 들어오면 실패하거나 프로세스를 종료해야 한다.
- 프로세스가 종료될 때 열린 fd를 정리해야 한다.
- `fork` 이후에는 fd 상속과 복제가 문제가 된다.
- `open()`으로 따로 얻은 서로 다른 fd들은 같은 파일을 가리켜도 file position을 공유하지 않는다.

Project 2 FAQ에는 `struct file *`를 그냥 캐스팅해서 fd로 쓰지 말라고 되어 있다. fd는 커널 내부 포인터를 숨기고, 프로세스별 자원 관리를 가능하게 하는 추상화로 보는 편이 좋다.

## 11. File System Lock이 필요한 이유

Project 2의 파일 시스템은 내부 동기화를 제공하지 않는다. 여러 프로세스가 동시에 파일 시스템 함수를 호출하면 자료구조가 꼬일 수 있다.

따라서 system call에서 파일 시스템에 들어가는 구간은 critical section으로 다뤄야 한다. 일반적으로 전역 file system lock을 두고, 파일 시스템 호출 전후로 acquire/release를 한다.

예를 들어 다음 system call은 파일 시스템 접근과 연결된다.

- `open`
- `create`
- `remove`
- `read`
- `write`
- `filesize`
- `seek`
- `tell`
- `close`
- `exec`

여기서 appendix의 `02_synchronization.md`가 필요하다. lock은 한 번에 하나의 스레드만 critical section에 들어가게 하는 도구다. 파일 시스템이 thread-safe하지 않기 때문에, Project 2에서는 lock을 통해 커널 쪽에서 안전하게 감싸야 한다.

주의할 점은 lock을 잡은 상태에서 잘못된 user pointer를 만나거나, 중간에 프로세스를 종료하게 될 때다. 이런 경우 lock을 놓지 않으면 이후 모든 파일 관련 system call이 멈출 수 있다. 그래서 user pointer 검증과 자원 정리는 함께 설계해야 한다.

또한 Project 2의 파일 시스템은 완전한 실제 파일 시스템이 아니다. 파일 크기는 생성 시점에 고정되고, 하위 디렉터리가 없으며, 파일 이름 길이에도 제한이 있다. 따라서 `write`가 파일 끝을 넘어간다고 해서 자동으로 파일이 커지는 것을 기대하면 안 된다. 이번 주의 초점은 파일 시스템 자체를 고치는 것이 아니라, 제한된 파일 시스템을 system call을 통해 올바르게 사용하는 것이다.

파일 삭제도 초심자가 헷갈리기 쉽다. PintOS의 `filesys_remove()`는 Unix와 비슷한 의미를 가진다. 어떤 파일이 삭제되더라도 이미 그 파일을 열고 있는 fd가 있으면, 그 fd를 통해서는 계속 접근할 수 있다. 파일은 이름만 사라지고, 마지막으로 열린 fd가 닫힐 때 실제 자원이 정리된다고 이해하면 된다.

## 12. Process Control: exit, wait, exec, fork

Project 2에서 가장 헷갈리는 부분은 프로세스 관계다. 네 system call의 차이를 먼저 잡아야 한다.

| system call | 의미 |
|---|---|
| `exit(status)` | 현재 프로세스를 종료하고 상태값을 남김 |
| `wait(pid)` | 자식 프로세스가 끝날 때까지 기다리고 exit status를 받음 |
| `exec(cmd_line)` | 현재 프로세스의 프로그램 이미지를 새 실행 파일로 교체 |
| `fork(thread_name)` | 현재 프로세스를 복제해 자식 프로세스를 만듦 |

`exit`는 끝나는 쪽의 동작이다. 프로세스는 자기 종료 상태를 기록하고, 열린 파일과 할당한 자원을 정리해야 한다. 공식 문서는 사용자 프로세스 종료 시 `프로세스이름: exit(status)` 형식의 메시지를 요구한다. 단, 사용자 프로세스가 아닌 커널 스레드가 종료할 때나 `halt` system call이 호출될 때는 이 메시지를 출력하지 않아야 한다.

`wait`는 기다리는 쪽의 동작이다. 부모는 자식의 종료 상태를 한 번만 받을 수 있다. 직계 자식이 아닌 프로세스를 기다릴 수 없고, 같은 자식을 두 번 wait할 수도 없다.

특히 초기 프로세스가 끝나기 전에 PintOS가 먼저 종료되면 안 된다. 그래서 `process_wait()`는 단순히 테스트를 통과하기 위한 함수가 아니라, 커널이 사용자 프로그램의 종료를 기다리는 기본 구조와 연결된다.

자식 프로세스가 정상적으로 `exit(status)`를 호출하고 끝났다면 부모의 `wait(pid)`는 그 status를 받아야 한다. 반대로 자식이 잘못된 메모리 접근 같은 예외 때문에 커널에 의해 종료되었다면, `wait(pid)`는 `-1`을 반환해야 한다. 즉, 부모는 "자식이 어떤 값으로 정상 종료했는가"뿐 아니라 "자식이 비정상적으로 죽었는가"도 알 수 있어야 한다.

`exec`는 새 프로세스를 만드는 것이 아니라 현재 프로세스의 실행 이미지를 바꾸는 동작이다. 성공하면 기존 프로그램으로 돌아오지 않는다. 실패하면 종료 상태 `-1`로 끝나야 한다. 원본 명세상 `exec` 호출 전후로 파일 디스크립터는 열린 상태를 유지하며, `exec`를 호출한 스레드의 이름도 바꾸지 않는다.

`fork`는 가장 복잡하다. 부모의 주소 공간과 fd 상태를 자식에게 복제해야 한다. 부모는 자식이 복제에 성공했는지 확인하기 전까지 `fork`에서 반환하면 안 된다. 이 요구사항 때문에 synchronization이 필요하다.

여기서 `tid_t`와 `pid_t`도 구분해야 한다. `tid_t`는 커널 스레드를 식별하는 값이고, `pid_t`는 사용자 프로세스를 식별하는 값이다. PintOS에서는 둘을 같은 정수값처럼 설계할 수도 있지만, 개념적으로는 서로 다른 역할을 한다. `wait` 같은 사용자 프로그램 인터페이스와 `process_fork()`/`process_wait()` 설계에서는 `pid_t` 관점이 중요하다.

초심자 관점에서는 다음 질문을 계속 붙잡는 것이 좋다.

- 부모는 자식의 종료 상태를 어디에서 찾는가?
- 자식이 먼저 죽으면 정보는 어디에 남아 있어야 하는가?
- 부모가 먼저 죽으면 자식 자원은 어떻게 정리되는가?
- `wait`는 왜 한 번만 허용되는가?
- `fork`에서 부모와 자식의 반환값은 왜 다른가?

## 13. Deny Write to Executables

실행 중인 파일이 디스크에서 동시에 수정되면 문제가 생길 수 있다. 프로세스가 어떤 코드를 실행하고 있는데, 그 실행 파일 내용이 다른 프로세스에 의해 바뀌면 예측하기 어렵다.

그래서 Project 2는 실행 중인 파일에 대한 쓰기를 막으라고 요구한다. 이를 위해 실행 파일을 열어 둔 상태로 `file_deny_write()`를 적용하고, 프로세스가 종료될 때 다시 정리해야 한다.

핵심은 "실행 파일을 잠깐 열고 닫으면 안 된다"는 점이다. 쓰기 금지를 유지하려면 프로세스가 실행되는 동안 해당 file 객체를 계속 들고 있어야 한다.

이 요구사항은 `rox-*` 테스트와 연결된다. `rox`는 read-only executable의 약자로 이해하면 된다.

## 14. dup2 Extra

`dup2`는 extra 요구사항이다. 기본 Project 2 통과와는 별개지만, 공지와 테스트 목록에 포함되어 있다면 팀 목표에 따라 다룰 수 있다.

`dup2(oldfd, newfd)`는 `oldfd`가 가리키는 열린 파일을 `newfd` 번호로도 가리키게 만든다. 이때 두 fd는 서로 다른 번호지만 같은 open file description을 참조한다. 그래서 file offset을 공유한다.

초심자에게 중요한 포인트는 다음이다.

- `oldfd`가 유효하지 않으면 실패한다.
- `newfd`가 이미 열려 있으면 조용히 닫고 재사용한다.
- `oldfd == newfd`이면 아무 일도 하지 않고 성공한다.
- `fork` 이후에도 dup된 fd의 의미가 유지되어야 한다.

이 기능은 fd table 설계가 단순 배열인지, 동적 구조인지, file 객체 참조를 어떻게 관리하는지에 영향을 준다. 따라서 extra를 할 계획이라면 처음 fd table을 설계할 때부터 고려하는 편이 좋다.

원본 문서는 extra 테스트에 부분 점수가 없다고 설명한다. 따라서 `dup2`는 "조금만 구현해도 일부 점수를 얻는 기능"이라기보다, 기본 Project 2 요구사항을 안정화한 뒤 팀 상황에 따라 도전할 기능으로 보는 편이 현실적이다.

## 15. 메모리 할당과 자원 정리

Project 2를 구현하다 보면 문자열 복사, fd table, child status 구조체, load synchronization 구조체 등을 위해 커널 메모리를 할당하게 된다.

appendix의 `03_memory_allocation.md`는 PintOS의 두 할당자를 설명한다.

| 할당자 | 용도 |
|---|---|
| page allocator | page 단위 할당 |
| block allocator | `malloc`, `calloc`, `free` 같은 임의 크기 블록 할당 |

초심자가 기억해야 할 점은 세 가지다.

- 실패할 수 있는 할당은 반드시 실패 처리를 해야 한다.
- 잘못된 user pointer나 load 실패가 발생해도 이미 잡은 자원을 해제해야 한다.
- user program의 잘못 때문에 커널이 panic하면 안 된다.

특히 Project 2는 "성공 경로"보다 "실패 경로"가 더 어렵다. 파일을 열었다가 이후 단계에서 실패하면 닫아야 하고, 메모리를 할당했다가 load에 실패하면 해제해야 한다. 자식 상태를 만들었다면 부모와 자식 중 누가 언제 해제할지도 정해야 한다.

## 16. 디버깅 관점

Project 2에서 자주 보는 증상은 다음과 같다.

| 증상 | 먼저 의심할 부분 |
|---|---|
| 모든 사용자 프로그램이 page fault | 스택 설정, argument passing, user address mapping |
| `system call!`만 출력되고 종료 | syscall handler 미구현 또는 번호 읽기 실패 |
| `args-*` 실패 | command parsing, stack layout, register 설정 |
| `bad-*` 실패 | user pointer validation |
| `wait-*` 실패 | parent-child 관계와 exit status 보관 |
| `rox-*` 실패 | 실행 파일 deny write |
| 랜덤한 hang | lock release 누락, wait semaphore 누락 |

appendix의 `06_debugging_tools.md`는 `printf`, `ASSERT`, backtrace, GDB 사용을 설명한다. 다만 공식 문서가 경고하듯, 최종 제출 코드에는 불필요한 출력이 남아 있으면 안 된다. 테스트 출력이 채점 기준과 달라질 수 있기 때문이다.

디버깅할 때는 한 번에 모든 테스트를 보지 말고, 테스트 이름을 요구사항처럼 읽는 것이 좋다.

- `args-*`: 인자 전달
- `halt`, `exit`: 기본 syscall
- `create`, `open`, `close`: fd table 기본
- `read`, `write`: buffer 검증과 파일 입출력
- `fork`, `exec`, `wait`: 프로세스 관계
- `bad-*`: 잘못된 주소와 비정상 입력
- `multi-*`, `syn-*`: 동시성, 반복, 자원 정리
- `rox-*`: 실행 파일 쓰기 금지

## 17. 구현 순서를 어떻게 잡으면 좋은가

처음부터 모든 system call을 한꺼번에 구현하려고 하면 흐름이 무너진다. 다음 순서로 개념과 테스트를 묶어 보는 편이 좋다.

| 순서 | 목표 | 이유 |
|---|---|---|
| 1 | argument passing | 사용자 프로그램이 정상적으로 시작해야 함 |
| 2 | `halt`, `exit` | syscall 진입과 종료 흐름 확인 |
| 3 | user pointer validation 기초 | 이후 모든 pointer 인자 syscall의 기반 |
| 4 | fd table, `open`, `close` | 파일 자원 관리의 뼈대 |
| 5 | `read`, `write` | buffer 검증과 stdin/stdout 처리 |
| 6 | `create`, `remove`, `filesize`, `seek`, `tell` | 파일 syscall 확장 |
| 7 | `exec`, load synchronization, `process_wait` 설계 | 프로그램 교체와 초기 프로세스 대기 흐름 |
| 8 | `fork`, `wait` 완성 | 주소 공간과 fd 복제, parent-child 동기화 |
| 9 | deny write, robustness, extra | 경계 조건과 추가 요구사항 |

이 순서는 절대적인 정답은 아니지만, 의존성을 고려한 학습 순서로는 자연스럽다. 예를 들어 fd table 없이 `read`와 `write`를 제대로 구현하기 어렵고, user pointer validation 없이 `bad-*` 테스트를 안정적으로 통과하기 어렵다. 또한 사용자 `wait(pid)`의 본격적인 검증은 `fork`로 자식을 만들 수 있어야 가능하므로, `wait`는 설계를 먼저 잡고 `fork` 이후에 완성하는 식으로 접근하는 편이 자연스럽다.

## 18. 낯선 용어를 초심자식으로 다시 보기

Project 2 문서에는 운영체제 용어가 많이 나온다. 처음 읽을 때는 아래처럼 단순하게 잡고 들어가면 흐름을 놓치지 않기 쉽다.

| 용어 | 쉽게 이해하기 |
|---|---|
| user program | 커널 위에서 실행되는 일반 프로그램 |
| kernel | 사용자 프로그램의 요청을 받아 자원을 관리하는 운영체제 본체 |
| process | 실행 중인 사용자 프로그램 한 개 |
| thread | CPU가 실제로 따라가는 실행 흐름 |
| context switch | CPU가 실행 중인 스레드나 프로세스를 다른 것으로 바꾸는 일 |
| stack | 함수 호출, 지역 정보, 인자 정보가 쌓이는 메모리 공간 |
| register | CPU 안에 있는 아주 빠른 임시 저장 공간 |
| pointer | 값 자체가 아니라 값이 있는 주소 |
| page | 메모리를 일정한 크기로 나눈 단위 |
| page table | 가상 주소가 실제 메모리 어디에 연결되는지 적은 표 |
| page fault | 접근할 수 없는 주소를 읽거나 쓰려고 할 때 발생하는 예외 |
| file descriptor | 열린 파일을 사용자 프로그램에 보여 주기 위한 정수 번호 |
| lock | 여러 스레드가 동시에 같은 자원을 건드리지 못하게 막는 도구 |
| semaphore | 어떤 사건이 일어날 때까지 기다리거나 깨우는 데 자주 쓰는 동기화 도구 |

이 용어들을 완벽히 외울 필요는 없다. 다만 Project 2를 읽을 때 "주소를 검증한다", "fd table을 관리한다", "부모가 자식을 wait한다", "파일 시스템 lock을 잡는다" 같은 문장이 무엇을 의미하는지 대략 떠올릴 수 있으면 된다.

## 19. 특강 전에 이해하고 갈 핵심 질문

특강을 듣기 전에는 아래 질문에 스스로 답해 보는 것이 좋다.

- Project 2에서 사용자 프로그램은 왜 커널 함수를 직접 호출할 수 없는가?
- system call이 발생하면 CPU 모드는 어떻게 바뀌는가?
- 커널은 왜 사용자 포인터를 믿으면 안 되는가?
- user address와 kernel address는 어떻게 구분하는가?
- 주소가 user 영역이면 항상 안전한가?
- file descriptor는 왜 단순한 정수 번호로 제공되는가?
- `exit`와 `wait`는 어떤 정보를 주고받는가?
- `exec`와 `fork`는 어떻게 다른가?
- 파일 시스템에 전역 lock이 필요한 이유는 무엇인가?
- 테스트 이름을 보면 어떤 요구사항을 검증하는지 추측할 수 있는가?

이 질문에 완벽하게 답하지 못해도 괜찮다. 다만 질문 자체가 익숙해지면 특강에서 함수 이름과 구현 세부사항이 나와도 큰 흐름을 놓치지 않을 수 있다.
