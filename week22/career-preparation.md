# Week 22 - 취업 준비 정리

> 목표 직무: 백엔드 개발, AI 플랫폼, LLMOps와 RAG 플랫폼 관련 직무

## 1. 나를 설명하는 방향

### 한 줄 소개 초안

기업용 AI Workflow를 설계하면서 권한 기반 RAG, 문서 수명주기와 실행 안정성 문제를 다룬 백엔드·AI 플랫폼 개발자 지망생입니다.

### 강조할 강점

1. 기능 구현 여부만 보지 않고 권한, 데이터 수명주기, 장애와 운영 경계를 함께 살펴본다.
2. 복잡한 문제를 요구사항, 정책, 구현 단계와 테스트 경계로 나누어 정리한다.
3. AI 에이전트를 적극적으로 활용하면서도 결과를 그대로 믿지 않고 검증 책임의 중요성을 배웠다.

### 보완해야 할 점

- AI 에이전트가 작성한 코드와 테스트를 직접 읽고 실행 결과를 확인하는 비중이 부족했다.
- 넓은 시스템 설계에 비해 한 기능을 처음부터 끝까지 직접 구현하고 설명하는 경험을 더 쌓아야 한다.
- 검색 품질, 부하와 운영 환경을 수치로 증명하는 경험을 보완해야 한다.

## 2. Nodease 프로젝트 설명

### 한 줄 설명

Nodease는 비개발자가 자연어로 AI Workflow를 만들고, 기업 내부 권한이 적용된 지식을 사용하며, 실행 비용과 감사 기록을 관리할 수 있도록 만든 기업용 AI Workflow·LLMOps 플랫폼이다.

### 해결하려 한 문제

- AI Workflow가 늘어나면서 비용과 실행 상태를 파악하기 어렵다.
- LLM 답변에 어떤 문서가 사용됐는지 확인하기 어렵다.
- 권한이 없는 문서가 검색 근거나 답변에 포함될 수 있다.
- 문서 변경, 삭제와 권한 회수가 실행 시점에 반영되지 않을 수 있다.
- 비동기 실행과 재시도로 외부 부수효과가 중복될 수 있다.

### 내가 담당한 범위

- Knowledge/RAG 요구사항과 책임 경계 정리
- KB, Document, Chunk, Document Version과 Knowledge Collection 개념 구분
- 조직, 팀, 사용자 기준의 KB 사용 권한과 관리 권한 위임 정책
- Workflow 저장, 배포 전 검사와 runtime 검색의 권한 계약 정리
- 문서 수집, parsing, chunking, embedding과 Active Version 전환 흐름
- no-evidence 정책과 사용자 Citation, 내부 Lineage 개념 구분
- 관련 Linear 이슈 분리, 구현 계획, 테스트 계획과 코드 리뷰 조치 관리

### 사용한 기술

| 기술 | 사용 이유 |
|---|---|
| FastAPI | 인증된 API 경계와 Knowledge 관리 API 구성 |
| SQLAlchemy, PostgreSQL | 조직·권한·문서 version과 실행 상태의 관계형 계약 관리 |
| pgvector | embedding vector 저장과 유사도 검색 |
| Celery, Redis | 비동기 문서 처리와 Workflow 실행 |
| Next.js, React | Workflow 편집, Knowledge 관리와 실행 결과 화면 |
| Docker, Helm, Kubernetes | 로컬·운영 배포 구성과 network policy 적용 |
| pytest, Vitest, Playwright | service, API, Client와 사용자 흐름 검증 |

### 구현에서 중요했던 판단

1. 신규 수동 문서는 독립적인 문서 한 개를 KB 한 개로 관리한다.
2. Knowledge Collection은 KB를 묶어 선택하고 운영하기 위한 단위이며 하위 KB 권한을 대신하지 않는다.
3. Workflow에 선택됐다는 이유만으로 실행 사용자에게 KB 권한이 생기지 않는다.
4. 새 문서 version의 chunk와 embedding이 준비되기 전에는 기존 Active Version을 유지한다.
5. 허용된 근거가 없으면 LLM provider를 호출하지 않는다.
6. 사용자 Citation에는 공개 가능한 정보만 담고 내부 resource 구조는 노출하지 않는다.

### 완성 범위를 설명할 때 주의할 점

- 외부 source ACL을 저장하고 fail-closed로 판정하는 계약은 있지만 모든 connector의 최신 ACL 갱신이 완성된 것은 아니다.
- 사용자 Citation은 구현됐지만 삭제 문서까지 장기간 추적하는 공통 Lineage 저장소는 완성되지 않았다.
- Workflow 실행 event는 SSE로 전달하지만 provider token을 생성 즉시 전달하는 full token streaming은 아니다.
- 예약 실행의 중복 시작은 막지만 모든 외부 서비스의 부수효과까지 exactly-once를 보장하지는 않는다.
- HTTPS와 egress proxy 설정은 있으나 실제 운영 환경 적용 여부는 배포 환경에서 확인해야 한다.

## 3. 프로젝트 경험 답변 구조

### 사례 1. 권한 판단이 계층마다 달랐던 문제

**상황**

Client에서 선택 가능한 KB와 배포 전 검사, Workflow runtime의 실제 검색 기준이 서로 달라질 수 있었다.

**접근**

저장 단계, 배포 전 검사와 runtime을 구분하고 실행 시점에는 현재 사용자, 조직, KB 상태와 source authorization을 다시 확인하도록 정책을 정리했다.

**결과**

Workflow 소유자의 권한이 실행 사용자에게 조용히 적용되는 문제와 삭제·권한 회수 이후 stale KB가 검색되는 경로를 차단할 수 있었다.

**배운 점**

보안 정책은 UI 안내가 아니라 실제 데이터를 소비하기 직전의 서버 경계에서 다시 확인해야 한다.

### 사례 2. 새 문서 version 실패가 기존 검색을 깨뜨리는 문제

**상황**

새 문서의 parsing, chunking이나 embedding이 중간에 실패했을 때 기존 정상 문서까지 검색되지 않을 수 있었다.

**접근**

새 version을 별도로 준비하고 모든 chunk와 embedding이 준비된 뒤에만 Active Version pointer를 전환하는 구조를 사용했다.

**결과**

새 version 처리 실패 중에도 기존 정상 검색을 유지할 수 있는 기준을 마련했다.

**배운 점**

비동기 데이터 파이프라인에서는 성공 경로뿐 아니라 부분 성공, retry와 전환 시점을 함께 설계해야 한다.

### 사례 3. 코드 리뷰에서 문제가 반복된 원인

**상황**

리뷰가 추가될 때마다 새로운 edge case가 발견됐다.

**접근**

개별 조건을 계속 덧붙이는 대신 같은 정책이 여러 module에 중복돼 있는지, 가짜 DB 테스트가 실제 SQL 의미를 놓치고 있는지 확인했다. service 분기, query 구조, PostgreSQL 계약과 화면 흐름을 목적별 테스트로 나눴다.

**결과**

문제를 한 줄씩 막는 방식에서 책임 경계와 공통 계약을 먼저 정리하는 방식으로 개발 절차를 개선했다.

**배운 점**

테스트 수보다 정책을 결정하는 위치와 실제 소비 경계를 검증하는 테스트가 중요하다.

## 4. 예상 질문

### Knowledge/RAG

1. KB와 Document를 왜 분리했는가?
2. 한 문서와 한 KB를 대응시킨 이유는 무엇인가?
3. Knowledge Collection이 하위 KB 권한을 상속하지 않는 이유는 무엇인가?
4. Workflow 소유자와 실행 사용자 중 누구의 권한으로 검색하는가?
5. 권한이 회수된 KB가 이미 배포된 Workflow에 연결돼 있으면 어떻게 되는가?
6. 문서 version 교체 중 실패하면 기존 검색은 어떻게 유지하는가?
7. 허용된 근거가 없을 때 왜 LLM 호출을 생략하는가?
8. Citation과 Lineage의 차이는 무엇인가?
9. embedding model이나 차원이 다른 문서를 함께 검색할 수 있는가?
10. source ACL이 stale이거나 확인에 실패하면 어떻게 처리하는가?
11. vector search의 품질은 어떤 지표로 평가하는가?
12. RAG prompt injection은 어떤 경계에서 다루는가?

### 백엔드와 분산 실행

1. Celery worker와 thread, greenlet의 차이는 무엇인가?

3. 예약 실행 중복 시작을 어떻게 막았는가?
4. transaction 안의 DB 변경과 외부 API 호출을 함께 처리할 때 어떤 문제가 생기는가?
5. PostgreSQL 계약 테스트가 가짜 Query 단위 테스트와 다른 점은 무엇인가?
6. fail-open과 fail-closed 중 어떤 기준으로 선택했는가?

### AI 활용

1. AI 에이전트에게 어떤 일을 맡겼는가?
2. AI가 작성한 코드의 정확성을 어떻게 검증했는가?
3. 직접 검증이 부족했던 부분은 무엇인가?
4. 다시 진행한다면 AI 활용 절차를 어떻게 바꾸겠는가?

## 5. 면접 답변 원칙

- 결론을 먼저 말하고 근거와 사례를 뒤에 붙인다.
- 설계한 내용과 실제 구현된 내용을 구분한다.
- 직접 확인한 사실과 AI 결과 보고에 의존한 내용을 구분한다.
- 모르면 모른다고 말한 뒤 아는 개념을 바탕으로 추론한다.
- 성능이나 품질 수치는 측정 근거가 있을 때만 말한다.
- 약점을 숨기기보다 원인과 다음 개선 계획까지 설명한다.

## 6. 지원 활동 운영

### 지원 전

- 채용 공고에서 필수 역량과 우대 역량을 구분한다.
- 내 경험과 연결되는 항목을 표시한다.
- 회사와 직무에 맞게 이력서 첫 문장과 프로젝트 순서를 조정한다.
- 링크와 개인정보를 확인한다.

### 지원 후

- 지원 일자, 직무와 공고 핵심 요구사항을 비공개 기록에 남긴다.
- 서류 결과와 피드백을 기록한다.
- 면접 질문, 답변하지 못한 부분과 보완 계획을 정리한다.
- 반복되는 부족한 역량을 다음 주 학습 계획에 반영한다.

### 역질문 후보

- 팀의 코드 리뷰와 장애 회고는 어떻게 진행되는가?
- AI 기능의 품질과 보안을 어떤 기준으로 검증하는가?
- 현재 팀이 해결하려는 가장 큰 기술적 문제는 무엇인가?

## 7. 공개 자료 보안 원칙

- 실제 이력서 원본과 연락처는 공개 저장소에 넣지 않는다.
- 지원 기업별 자료와 지원 결과는 비공개로 관리한다.
- credential, `.env`, 내부 서버 주소와 원본 audit payload를 공개 자료에 포함하지 않는다.
- 프로젝트 화면을 사용할 때 실제 사용자 정보와 secret이 보이지 않는지 확인한다.
